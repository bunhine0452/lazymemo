## 문제 정의

windows의 stickynotes, https://www.desktopcal.com/kor/ 와 같은 메모장 어플을 만들것이다.

게으른 메모장의 철학은 사용자는 게으르며, 이 게으름을 타파할수있게 도와주는 메모장이다.
이 메모장은 메모리를 최소한으로 잡아먹으며 이에 맞는 프레임워크들을 이용한다.
LLM을 사용하여 메모를 정할수있다. claude desktop 과 연동되고, 쉽게 호출할수있다.
다른 LLM 호출 방식(ollama, openrouter 는 추후 지원)
바탕화면에 보여야하며, 쉬운 편집을 위해 상단바에도 보여야한다. (일단 mac만 지원)
아마추어같은 디자인은 절대 안된다. lazymemo는 정교한 설계 (UX와,프론트엔드를 매우 신경쓴다. 아이콘 모양까지!)


#### 목표
이 프로젝트가 끝나면 무엇이 가능해지나.

> 아래는 claude-code 의 **제안** — 확정 전까지 초안으로 취급.

- 전역 단축키 한 번으로 메모를 남기고, 앱을 "열지" 않아도 바탕화면에 계속 보인다.
- 메뉴바 아이콘에서 즉시 입력·검색·편집이 된다.
- Claude Desktop 에서 대화하다가 "이거 메모해 둬" 라고 하면 바탕화면 메모로 꽂힌다.
- 쌓인 메모를 LLM 이 정리·분류·요약해 준다 (게으름 타파의 실체).

#### 성공 기준
측정 가능한 형태로.

> 아래는 claude-code 의 **제안** — 숫자는 초안이며 프레임워크 결정 후 스파이크로 검증 필요.

- 메모 10장 표시 상태에서 앱 전체 RSS 합계 ≤ 100MB (참고 실측치는 배경 섹션).
- 아무 조작 없이 표시만 하고 있을 때 CPU 0% (애니메이션·폴링 타이머 없음).
- 전역 단축키 입력 → 커서가 깜빡이는 입력 상태까지 ≤ 150ms.
- 생각 → 저장 완료까지 조작 2회 이내 (단축키 + 타이핑, 저장 버튼 없음 = 자동 저장).
- 재부팅 후 메모 내용·위치 100% 복원, 외부 모니터 연결/해제 왕복 후에도 좌표 유실 0건.
- 한글 IME 조합 중 자모 유실·커서 점프 0건 (메모장의 본질 기능이므로 별도 기준으로 둔다).

### 개발 환경 실측 (이 머신)

- macOS **26.5.2** (build 25F84) — Tahoe. 시스템 디자인 언어가 **Liquid Glass**.
- Swift 6.3.3 사용 가능하지만 `xcode-select` 활성 경로가 `/Library/Developer/CommandLineTools` → **Xcode 미설치**. 네이티브 앱 번들 경로를 고르면 Xcode 설치(수 GB)가 선행 비용.
- Rust 1.95.0 / Node 26.7.0 / npm 11.19.0 / pnpm 10.33.2 설치됨 → Tauri 경로는 오늘 바로 시작 가능.
- ollama 미설치 (문제 정의의 "추후 지원" 순서와 일치).
- `claude` CLI (Claude Code 2.1.241) 설치됨.

### Claude Desktop 연동 표면 실측

`/Applications/Claude.app/Contents/Info.plist` 및 설정 파일을 직접 확인한 결과:

- `CFBundleURLSchemes` 에 **`claude`** 스킴 등록됨 → 외부 앱이 Claude Desktop 을 **열 수는** 있다. 단 URL 스킴은 단방향이라 **결과를 돌려받지 못한다**.
- `NSAppleScriptEnabled` 없음, `.sdef` 없음 → **AppleScript 자동화 불가**.
- `~/Library/Application Support/Claude/claude_desktop_config.json` 에 `mcpServers` 키 존재 (현재 비어 있음) → **공식 확장점은 MCP 서버 등록이 유일**.
- `Contents/Frameworks/` 에 `Electron Framework.framework`, `Claude Helper (Renderer/GPU/Plugin).app`, `Squirrel.framework` → Claude Desktop 자체가 Electron 앱.

### 메모리 참고 실측 (동일 머신, 동시각)

- Claude Desktop (Electron): **25 프로세스 / RSS 합계 1,662MB**.
- 네이티브 시스템 UI 앱: Dock **15MB**, ControlCenter **60MB**, NotificationCenter **83MB**, UserNotificationCenter 12MB.

→ "메모리 최소" 목표의 현실적 눈금은 수십 MB대(네이티브 시스템 UI 수준)이지 수백 MB대가 아니다.

### 경쟁·참고 제품

- **Stickies.app** — `/System/Applications/Stickies.app` 에 이미 설치되어 있는 macOS 기본 포스트잇. 무료·상시 설치·메모리 미미. "왜 이걸 두고 lazymemo 를 쓰나"에 답하지 못하면 성공 기준이 서지 않는다.
- **Raycast Notes** — 전역 단축키 + 플로팅 노트 + AI 를 이미 무료로 제공. 가장 가까운 경쟁자.
- Windows Sticky Notes / DesktopCal — 문제 정의에 명시된 레퍼런스.

### 방안 C — 네이티브 SwiftUI + AppKit 단일 앱 (프레임워크 축) {#opt-c}

- 장점:
  - **Liquid Glass 를 공짜로 얻는다.** 이 머신은 macOS 26.5.2 이고 시스템 재질·모서리·그림자·모션이 OS 에서 온다. "아마추어 같은 디자인 절대 금지" 요구에서 가장 확실한 수단은 시스템 디자인 언어를 재구현하지 않는 것이다.
  - **SF Symbols** 수천 개를 굵기·광학 크기 정합까지 무료로. "아이콘 모양까지 신경 쓴다"는 요구와 정확히 맞물린다.
  - **한글 IME 조합을 OS(NSTextView)가 처리**한다. 웹뷰 contenteditable 의 한글 조합 깨짐은 한국어 메모장에서 부가 리스크가 아니라 핵심 리스크다.
  - 메모리: 창당 비용이 웹뷰 대비 자릿수로 싸다. 위 실측의 Dock 15MB / ControlCenter 60MB 대역이 현실적 목표가 된다.
  - `NSStatusItem` + `NSPopover` 로 메뉴바 UI 가 기본 제공. 바탕화면 창(`NSWindow.level`)도 우회 없이 직접 다룬다.
- 단점:
  - ~~Xcode 설치가 선행~~ → **정정됨. 2026-08-28 실측 결과 Xcode 없이 CommandLineTools 만으로 빌드된다** (아래 검증 블록 참조).
  - Swift/SwiftUI + AppKit 상호운용 학습 곡선. 웹 프론트엔드 자산을 재사용할 수 없다.
  - 디자인 반복 속도가 웹보다 느리다 (핫리로드가 브라우저 수준은 아님).
- 비용: Swift 학습만 남는다. 이 앱의 최난도 구간(바탕화면 창 레벨, 메뉴바, IME)은 어차피 AppKit 영역이므로 학습이 헛되지 않는다.

**검증 (2026-08-28, 이 머신에서 실제 빌드·실행함)** — `swift-tools-version: 6.2` + SPM executableTarget 하나로 아래가 **전부 컴파일되고 런타임에 동작**했다. Xcode 미설치, Apple 계정 없음, 32.57초 빌드:

- `import SwiftUI` + `.glassEffect()` → **Liquid Glass API 가 SDK 26.5 에 있고 컴파일된다**
- `NSStatusBar.system.statusItem(...)` + `NSImage(systemSymbolName:)` → 메뉴바 + SF Symbols
- `NSWindow.level = CGWindowLevelForKey(.desktopIconWindow) + 1`, `collectionBehavior = [.canJoinAllSpaces, .stationary]`, `isOpaque = false` → **바탕화면 레벨 투명 창**
- `NSApp.setActivationPolicy(.accessory)` + `LSUIElement` → Dock 아이콘 없는 상주 앱
- `.app` 번들 수동 조립 + `codesign -s -` (ad-hoc) 성공 — 유료 계정 불필요
- 실행 로그: `OK: statusItem + desktop-level NSWindow + SwiftUI glassEffect all constructed`

즉 방안 C 의 착수 장벽은 **Swift 학습 하나뿐**이고, 툴체인 비용은 0 이다.

### 방안 D — Tauri v2 (Rust + WKWebView) (프레임워크 축) {#opt-d}

- 장점:
  - Rust 1.95 / Node 26 이 이미 깔려 있어 **오늘 바로 시작** 가능. Xcode 선행 설치 불필요.
  - 웹 프론트엔드 생태계로 UI 반복이 빠르다. Electron 대비 훨씬 가볍다.
  - 나중에 Windows/Linux 로 넓힐 여지 (지금은 범위 밖이지만).
- 단점:
  - **바탕화면 창 레벨·Space 동작·메뉴바 팝오버는 결국 `objc2`/`cocoa` 로 NSWindow 를 직접 조작해야 한다.** 즉 웹 스택이 이 앱의 가장 어려운 부분을 없애주지 않고, 디버깅 층만 하나 늘린다. "웹으로 빨리 만든다"는 이점이 정작 난도 높은 구간에는 적용되지 않는다.
  - **창마다 WKWebView 가 생기고 WebKit 은 컨텐츠를 별도 프로세스에서 돌린다.** 프로세스 공유 여부는 설정에 달려 있어 보장되지 않는다. 포스트잇 10장 = 창 10개 구성이면 메모리 목표와 정면 충돌할 수 있다 → **E 의 오버레이 구조가 사실상 필수**가 된다.
  - Liquid Glass 를 `backdrop-filter` 등으로 흉내내야 하고, OS 업데이트마다 톤이 어긋난다. 아이콘 세트도 직접 준비·정합해야 한다.
  - 한글 IME 조합 리스크를 스스로 떠안는다.
- 비용: 낮은 착수 비용, 높은 후반 비용. **선택 시 스파이크 필수** — 투명 창 3~10개를 띄우고 WebContent 프로세스 수와 RSS 를 실측해 성공 기준의 100MB 를 지킬 수 있는지 먼저 확인할 것.

### 방안 E — 창 구조: 메모당 창 vs 투명 오버레이 1창 (창 축) {#opt-e}

메모 N개를 어떻게 화면에 올릴지는 프레임워크와 독립된 결정이며, 메모리 목표를 실제로 좌우하는 것은 이 축이다.

- **E-1 메모당 창 하나** — 드래그·리사이즈·z-order 를 OS 가 처리하고 접근성(VoiceOver)도 공짜. 네이티브(C)에서는 창당 수 MB라 자연스러운 선택.
- **E-2 전체화면 투명 오버레이 창 1개** 위에 메모를 그림 — 웹뷰가 하나로 끝나 D 의 메모리 문제를 해결. 대신 드래그·히트테스트·다중 디스플레이·클릭 통과(`ignoresMouseEvents`)를 전부 직접 구현해야 하고, 접근성도 직접 채워야 한다.
- 판단: **C 를 고르면 E-1, D 를 고르면 E-2 가 사실상 강제**된다. 즉 이 축은 프레임워크 결정에 종속된다.
- 공통 리스크(어느 쪽이든 검증 필요): Stage Manager, Mission Control, Sonoma+ 의 "월페이퍼 클릭 시 데스크탑 표시", 전체화면 앱 위에서의 동작, 다중 디스플레이 연결/해제 시 좌표 복원.

### 방안 F — LLM 경로: 방향이 두 개이고 한 방향은 막혀 있다 (LLM 축) {#opt-f}

문제 정의의 "claude desktop 과 연동되고, 쉽게 호출할수있다" 는 실측 결과 **두 개의 서로 다른 요구가 섞여 있다.**

- **F-1 바깥→안 (Claude Desktop 이 lazymemo 를 호출).** lazymemo 가 **MCP 서버**를 노출하고 `claude_desktop_config.json` 의 `mcpServers` 에 등록. `create_memo` / `list_memos` / `update_memo` 같은 도구를 열어 두면 Claude Desktop 에서 대화 중 메모가 바탕화면에 꽂힌다.
  - 장점: **API 키 불필요, 토큰 비용은 사용자의 Claude 구독이 부담.** 공식 확장점이라 안정적. 제품적으로 가장 큰 차별점.
  - 단점: 사용자가 Claude Desktop 을 열고 말을 걸어야 한다.
- **F-2 안→바깥 (lazymemo 가 LLM 을 호출).** "메모 정리" 버튼을 앱 안에 두려면 필요한데, **Claude Desktop 경유로는 불가능**하다. URL 스킴은 결과를 돌려주지 않고 AppleScript 도 막혀 있다. 따라서 별도 경로가 필요하다.
  - (a) Anthropic API 키 직접 — 키 관리(Keychain 저장) + 사용자가 비용 부담.
  - (b) `claude` CLI 서브프로세스 (`claude -p`) — 이 머신에 이미 설치됨. 구독 인증을 재사용할 수 있지만 CLI 존재·버전에 의존.
  - (c) ollama / openrouter — 문제 정의상 추후.
- 판단: **F-1 과 F-2 는 택일이 아니라 둘 다 필요**할 수 있다. 다만 F-1 이 비용·안정성 면에서 압도적이므로 **F-1 을 1차 범위로, F-2 는 그 다음**으로 두는 것이 맞다.
- 부수 리스크: **LLM 이 메모를 고친다 = 데이터 손실 위험.** 되돌리기 또는 변경 이력이 없으면 첫 오작동에 신뢰가 끝난다. 프라이버시(메모 본문이 외부로 나감)도 명시적 동의 지점이 필요하다.

### 방안 G — 저장: 메모당 마크다운 평문 파일 (저장 축) {#opt-g}

- 장점:
  - **F-1 의 MCP 연동이 거의 공짜가 된다** — 도구가 파일을 읽고 쓰면 끝.
  - iCloud Drive 폴더에 두면 동기화가 공짜 (백엔드 구축 없이).
  - 사용자가 직접 열어보고 다른 도구로 옮길 수 있다 = 게으른 사용자의 탈출구, 잠금 없음.
  - 되돌리기/스냅샷을 파일 복사로 싸게 구현 (F 의 데이터 손실 리스크 완화).
- 단점: 검색·정렬·태그 쿼리를 직접 구현해야 한다. 메모 수천 장에서는 인덱스가 필요.
- 대안(SQLite): 쿼리는 강하지만 외부 도구 연동이 전부 코드 작업이 되고 사용자가 내용을 못 본다.
- 비용: 지금 정하지 않으면 나중에 마이그레이션 비용이 붙는다. **되돌리기 비싼 결정이므로 착수 전 확정 대상.**

### 방안 H — 캘린더를 어떻게 넣나: 자체 뷰 우선, EventKit 은 읽기 연동 (데이터 축) {#opt-h}

1번 답변으로 **캘린더가 범위에 새로 들어왔다.** 메모에 날짜·시간·반복이 붙는 순간 그것은 이벤트이고, 이건 G(평문 파일) 의 전제를 흔든다.

- **H-1 자체 캘린더 (권장, 1차)** — 메모 frontmatter 에 `due` / `at` 필드를 두고 앱이 직접 캘린더 뷰를 그린다. 의존성 0, 권한 요청 0, 바탕화면 캘린더(DesktopCal 레퍼런스)와 정확히 일치.
- **H-2 EventKit 연동 (2차)** — macOS 기본 캘린더의 기존 일정을 함께 표시하고 시스템 알림을 공짜로 얻는다. 대신 TCC 권한 프롬프트가 필요하고, 쓰기까지 열면 사용자의 실제 캘린더를 LLM 이 건드리게 되어 위험이 급상승한다. **읽기 전용으로 시작할 것.**
- 저장 형식 보정: 메모 본문은 G 대로 마크다운 파일이 정본(source of truth)이되, 날짜 범위 쿼리는 파일에서 파생한 **SQLite 인덱스를 캐시로** 둔다. 인덱스는 언제든 파일에서 재생성 가능하므로 G 의 장점(사용자가 직접 열람·이동 가능)을 잃지 않는다.
- **LLM 이 스스로 삭제한다는 요구 때문에 되돌리기가 선택이 아니라 필수가 됐다.** 삭제는 즉시 삭제가 아니라 `.trash/` 이동 + N일 보존으로 구현한다. 파일 기반이라 비용이 거의 없다.

### 방안 I — 오픈소스 배포: 공증 없이 시작하고 나중에 붙인다 (배포 축) {#opt-i}

2번 질문에 대한 실측 답. **공증 없이도 가능하다. 그리고 이건 Swift 문제가 아니다.**

- **개발·본인 사용은 전혀 문제 없다** — 로컬 빌드 산출물에는 `com.apple.quarantine` 속성이 붙지 않아 Gatekeeper 평가 대상 자체가 아니다. ad-hoc 서명(`codesign -s -`)으로 충분하고 Apple 계정도 필요 없다 (실측 확인).
- **배포는 걸린다** — quarantine 속성을 부여하고 `spctl -a -t exec` 를 돌리면 `rejected` 가 나온다 (실측 확인). 단 이 거부는 **다운로드된 앱 번들**에 걸리는 것이라 **Tauri·Electron 으로 만들어도 똑같이 거부된다.** 공증은 언어·프레임워크와 무관하므로 **프레임워크 선택 기준이 아니다.**
- 오픈소스에서의 실제 선택지:
  - **I-1 소스 배포 + 사용자가 직접 빌드 (1차 권장)** — quarantine 이 안 붙어 공증이 아예 불필요. `swift build` 한 줄로 끝나는 것을 확인했으므로 진입장벽이 낮다.
  - **I-2 Homebrew cask** — 오픈소스 맥 앱의 표준 경로. cask 에서 quarantine 을 떼는 옵션을 쓸 수 있다.
  - **I-3 GitHub Releases 바이너리 + 안내** — macOS 15 부터 우클릭-열기 우회가 사라져 사용자가 시스템 설정 → 개인정보 보호 및 보안 → "확인 없이 열기" 로 가야 한다. 마찰이 크므로 단독으로는 권하지 않는다.
  - **I-4 Developer ID (연 $99)** — 사용자가 늘면. `notarytool` 이 이미 CommandLineTools 에 있어 인증서만 발급받으면 CI 에서 자동 공증이 가능하다. **나중에 붙일 수 있으므로 지금 결정할 필요가 없다.**
- 오픈소스이므로 파생 결정 하나: **API 키를 저장소에 넣을 수 없다.** 이는 F-1(MCP 서버, 키 불필요) 을 1차로 두는 근거를 더 강화한다.
- 필요 산출물: 라이선스 파일(MIT 등), README 의 빌드·설치 안내, 스크린샷.

## 결론

**채택: C + E-1 + F-1(1차) + G(H 보정) + I-1.**

- **프레임워크 = 방안 C, 네이티브 SwiftUI + AppKit.** C 를 막던 유일한 실질 반론이 "Xcode 선행 설치"였는데 2026-08-28 실측으로 뒤집혔다 — Xcode 없이 CommandLineTools 만으로 Liquid Glass·메뉴바·바탕화면 레벨 창이 전부 빌드·실행됐고 ad-hoc 서명으로 `.app` 번들까지 만들어졌다. 반대로 D(Tauri)의 단점은 그대로 남는다: 최난도 구간(NSWindow 레벨·메뉴바)에서 어차피 AppKit 을 만져야 하고, 창당 웹뷰 메모리가 100MB 목표와 충돌하며, Liquid Glass 와 SF Symbols 를 손으로 재현해야 하고, 한글 IME 리스크를 자초한다. **"메모리 최소"와 "아마추어 디자인 금지"를 동시에 요구하는 이상 네이티브가 유일하게 두 조건을 함께 만족한다.**
- **창 구조 = E-1**, 메모당 NSWindow. 네이티브에서는 창당 비용이 싸고 드래그·리사이즈·접근성을 OS 가 처리한다.
- **LLM = F-1 우선.** Claude Desktop 연동은 lazymemo 가 MCP 서버가 되는 방향만 성립한다(URL 스킴 단방향, AppleScript 불가 — 실측). 오픈소스라 API 키를 저장소에 넣을 수 없다는 점이 이 선택을 더 강화한다. F-2 는 앱 내 버튼이 필요해질 때 `claude` CLI 서브프로세스로 붙인다.
- **저장 = G + H.** 메모당 마크다운 파일이 정본, 날짜 쿼리는 파일에서 재생성 가능한 SQLite 파생 인덱스. 캘린더는 H-1 자체 뷰로 시작하고 EventKit(H-2)은 읽기 전용으로 나중에.
- **삭제 = 되돌리기 필수.** "LLM 이 스스로 삭제"가 확정 요구가 된 이상 즉시 삭제는 금지하고 `.trash/` 이동 + 보존 기간으로 구현한다.
- **배포 = I-1.** 공증 없이 소스 빌드로 시작한다. 공증은 프레임워크와 무관한 문제이므로 프레임워크 결정에 영향을 주지 않으며, `notarytool` 이 이미 있어 나중에 CI 로 붙일 수 있다.

**남은 미결(착수를 막지 않음):** 캘린더 UI 가 바탕화면 상주형인지 메뉴바 팝오버형인지, EventKit 연동 시점, Homebrew cask 등록 시점.
