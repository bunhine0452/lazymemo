## 문제 정의

LazyMemo는 입력·달력·바탕화면 메모·알림·검색·AI·길찾기를 이미 갖고 있다. 문제는 기능의 개수가 아니라 **사용자가 적은 것을 믿고 잊어도 되는가, 다시 만났을 때 바로 처리할 수 있는가**다. 이번 보고서는 홍보와 설치 문제를 넘어 이 기능적 약속을 검토한다.

**내 판단: 나는 현재 앱을 가벼운 바탕화면 메모로는 시험해 보겠지만, 놓치면 곤란한 할 일을 맡기는 주 도구로는 아직 선택하지 않겠다.** 날짜가 지났다는 이유로 미완료 내용이 뒤로 물러나고, 입력 문장의 형태가 저장 여부를 바꾸며, 기기와 입력 경로에 따라 알림 준비 상태가 달라지기 때문이다. 이는 실제 사용 체험담이 아니라 아래 코드·테스트에 근거한 제품 판단이다.

내가 맡는다면 제품의 중심을 **“흩어진 할 일과 자료를 바로 받아 두고, 놓친 것은 남겨 두며, 필요한 순간 원문과 다음 행동을 함께 꺼내 주는 개인 메모 도구”**로 좁힌다. 새 앱으로 모든 기록을 옮기게 하지 않고, 오늘 놓치기 쉬운 몇 가지를 맡기는 보조 도구로 시작한다.

### 조사 범위와 근거의 강도

- 현재 로컬 코드, 관련 테스트 원문, 과거 기능·버그 일지, 활성 플래너, 기존 제품·벤치 보고서를 읽었다. 워킹트리에는 다른 세션의 변경이 있으므로 로컬 최신 구현과 공개 배포판은 같다고 가정하지 않았다.
- 기존 빌드로 `./scripts/test.sh --skip-build --filter 'RecallTests|TidyRuleTests|CommandResolverTests|ConflictSettlementTests'`를 실행했다. 이름 부분 일치로 선택된 7개 스위트의 **46개 테스트가 통과**했다. 기존 바이너리이므로 최신 소스 전체의 회귀 검증은 아니다.
- 앱을 직접 조작하거나 새 사용자에게 사용시킨 결과는 없다. 실기기 알림·동기화·프레임 성능도 이번에 측정하지 않았다.
- **확인**은 코드나 테스트가 명시한 동작, **정적 결함 후보**는 코드 경로를 조합하면 충돌하지만 실행 재현이 남은 항목, **가설**은 사용자 관찰이 필요한 해석을 뜻한다.
- 이전 유입 조사는 [별도 보고서](../../../docs/research/adoption-audit-2026-09-22.md)에 있다. 적은 다운로드는 아래 기능 문제가 이탈을 일으켰다는 증거가 아니다.

## 기능 진단

### 1. 미완료와 지난 일정을 구분하지 못한다 — 최우선

**확인:** `Recall.nowCards`는 오늘 다시 보기·오늘 일정·고정만 고른다. 고정되지 않은 어제의 다시 보기는 자정 뒤 빠진다. `RecallTests.midnightMovesOn`이 이 동작을 명시한다. `Tidy.reason`은 일정 다음 날이 끝나면 `.past`를 반환하며, 이 날짜 판정은 미완료 체크리스트 여부보다 앞에 있다.

**사용자 장면:** 월요일까지 제출할 서류를 적었지만 못 끝냈다. 화요일에는 ‘지금’에서 빠지고 수요일에는 자동 정리 대상이 된다. 검색과 달력에는 남으므로 파일 유실은 아니다. 하지만 사용자가 기억하지 않아도 다시 보여 주겠다는 효용은 약해진다.

**변경:** 날짜 경과를 완료로 취급하지 않는다. 미처리 항목을 ‘놓친 것’으로 남기고, 완료·다시 보기·보관을 분리한다. 처음 적을 때 메모/할 일 종류를 고르도록 강요하지 않는다. 체크박스·다시 보기 지정 등 명확한 의도가 있으면 미처리로 취급하고, 일반 과거 일정은 조용히 접어 둔다. 사용자가 자동 정리를 선택하지 않은 미완료 항목은 치우지 않는다.

**통과 조건:** 날짜가 있는 미완료 체크리스트와 미확인 다시 보기가 자정·재시작·이틀 경과 뒤에도 발견 가능하다. 완료한 항목은 같은 이유로 다시 알리지 않는다. 놓친 항목을 매일 모두 푸시하는 방식은 피한다.

근거: [Recall.swift](../../../Sources/LazyMemoCore/Agenda/Recall.swift), [Tidy.swift](../../../Sources/LazyMemoCore/Model/Tidy.swift), [RecallTests.swift](../../../Tests/LazyMemoCoreTests/RecallTests.swift), [TidyRuleTests.swift](../../../Tests/LazyMemoCoreTests/TidyRuleTests.swift).

### 2. 미래의 다시 보기와 자동 정리가 충돌한다 — 정적 결함 후보

**확인:** `Tidy.reason`은 미래 `surface`를 예외로 보지 않는다. 정리 뒤에는 `Recall.eligible`이 `tidied != nil`인 메모를 예약에서 제외한다. `MemoService.update`는 잠시 `tidied`를 해제하지만 다음 정리에서 과거 일정 조건이 다시 적용될 수 있다.

**재현할 사례:** 9월 20일 일정의 다시 보기를 9월 25일로 설정하고, 9월 22일 정리를 실행한다. 고정·반복이 없는 경우 과거 일정으로 정리되고, 알림 대조가 실행되면 미래 예약 대상에서 제외되는 경로다. 사용자가 명시한 미래 약속을 자동 정리가 덮는다.

**추가 후보:** `untidy`는 `updated`를 갱신해 재정리를 피한다고 설명하지만, 지난 일정 판정은 `updated`를 읽지 않는다. 사용자가 꺼낸 과거 일정이 다음 정리 때 다시 치워질 수 있다.

**변경:** 미래 다시 보기와 명시적 복원은 자동 정리보다 우선한다. 복원 유지 정책을 데이터로 표현하거나 과거 일정 자동 정리를 제한한다. 주석만 고칠 일이 아니다.

**통과 조건:** 미래 다시 보기의 예약이 정리·재시작을 통과한다. 꺼내 둔 메모가 정리 한 번으로 다시 사라지지 않는다. 두 사례는 수정 전에 현재 소스로 회귀 테스트를 만들어 재현한다.

근거: [MemoService.swift](../../../Sources/LazyMemoCore/Storage/MemoService.swift), 위 Recall·Tidy 규칙.

### 3. 메모하려는 문장이 AI 질문이나 명령이 될 수 있다 — 높은 우선순위

**확인:** 질문 판정은 물음표 또는 ‘뭐·언제·어디·왜·어떻게…’ 등의 부분 문자열을 사용한다. 명령도 ‘폴더·알림·지워…’를 검사한다. 맥 `commit`과 폰 `leave`는 이 분기를 일반 메모 생성보다 먼저 처리한다. 폰은 비서가 연결된 경우에 해당한다.

**사례:** ‘왜 고객이 이탈할까?’라는 연구 주제를 남기거나 ‘어디서든 일하기’라는 아이디어를 적어도 질문으로 분류되는 코드 경로다. ‘알림 문구 아이디어’는 명령 동사를 포함한다. 이것은 문법적으로 질문인가의 문제가 아니라 **그 문장을 기록하려는 사람의 의도**를 구별하지 못하는 문제다.

**변경:** 기본 확정은 늘 ‘메모 남기기’로 유지한다. 질문처럼 보이면 ‘메모에서 답 찾기’를 보조 행동으로 제안하고, 명령은 명시적 선택 또는 이미 열린 비서 대화 안에서 실행한다. 검색은 함께 보여 줄 수 있지만 선택하지 않은 결과가 저장 동작을 가로채지 않게 한다. 최소 변경안은 항상 보이는 ‘그대로 메모’ 탈출구다.

**통과 조건:** 물음표·명령형·날짜·‘알림’이 포함된 아이디어 30개를 원문 그대로 저장할 수 있다. 모델 미설치·오프라인·추론 실패가 기록을 막지 않는다. 사용자가 확정 전에 결과를 설명할 수 있다.

근거: [CommandResolver.swift](../../../Sources/LazyMemoAssistant/CommandResolver.swift), [QuickCaptureModel.swift](../../../Sources/LazyMemoUI/QuickCapture/QuickCaptureModel.swift), [PenModel.swift](../../../ios/LazyMemo/PenModel.swift).

### 4. 저장과 알림 예약은 다른데 결과가 충분히 구분되지 않는다

**확인:** 날짜만 있는 메모에는 시스템 알림이 없다. 알림은 기기별로 기본 꺼짐이다. 공유 확장은 `InboxDrop.drop`으로 파일을 남기고, 일반 Recall 예약은 본 앱이 파일을 읽어 반영하는 구조다. 공유 확장의 출발지 질문 알림은 별도 기능이며 일정 시각 알림을 대신하지 않는다.

**사용자 장면:** 다른 앱에서 ‘내일 3시 제출’을 공유하고 앱을 다시 열지 않는다. 저장 완료를 알림 준비 완료로 받아들이면 기대가 어긋난다. ‘내일 제출’처럼 시각 없는 항목은 별도 선택 없이 울리지 않는다. 두 기기에서 알림을 켜면 각각 울릴 수 있다.

**변경:** 저장 직후 ‘메모 저장됨’, ‘이 iPhone에서 내일 15:00 알림 예약됨’, ‘알림 꺼짐’, ‘앱에서 예약 확인 필요’를 실제 상태에 맞게 구분한다. 첫 명시적 알림 요청 때 권한을 설명하고 요청한다. 날짜만 있으면 사용자가 선택할 수 있는 기본 알림 시간을 제안하되 말없이 정하지 않는다. 공유 확장에서도 예약할 수 있는 공통 경로를 검토하고, 보장할 수 없는 경우 명확하게 본 앱으로 연결한다.

**통과 조건:** 본 앱·공유·Siri 각각에서 생성 → 앱 종료 → 잠금 → 예정 시각 시나리오를 실기기로 확인한다. 다른 기기의 삭제·변경을 못 받은 상태와 동기화 이후 상태도 별도로 확인한다. 서버 없는 현재 구조에서 종료된 모든 기기에 즉시 반영된다고 약속하지 않는다.

근거: [ShareViewController.swift](../../../ios/LazyMemoShare/ShareViewController.swift), [ReminderCenter.swift](../../../Sources/LazyMemoReminders/ReminderCenter.swift), [RECALL_PLAN.md](../../../docs/RECALL_PLAN.md).

### 5. ‘봤어요’, 완료, 보관, 미루기가 사용자에게 다른 결과를 만든다

**확인:** ‘봤어요’는 기기별 등장 기록이다. 다른 기기 완료 처리와 같지 않다. 고정 메모는 다음 날 다시 등장할 수 있다. ‘하루 미루기’는 일정 이동이고, ‘한 시간 뒤 다시 보기’는 `surface` 변경이다. 일반 메모에는 명시적 완료 필드가 없다.

**변경:** 화면에 상황별 주 행동을 둔다. 할 일은 ‘완료’, 참고 자료는 ‘보관’, 아직 해야 하면 ‘나중에’. ‘나중에’에서 일정 자체를 옮기는지 다시 볼 때만 바꾸는지 결과를 짧게 보여 준다. ‘봤어요’는 유지한다면 ‘오늘 숨기기’처럼 제한된 의미를 드러낸다. 모든 메모에 단추 네 개를 상시 늘어놓지는 않는다.

**데이터 원칙:** 완료는 사용자 의사이므로 기기 간 공유한다. 잠시 화면에서 숨김은 기기별로 둘 수 있다. 반복 항목은 회차별 완료와 다음 회차를 구분해야 하며, 날짜 이동만으로 체크박스가 어떻게 되는지 별도 설계·검증한다.

**통과 조건:** 폰에서 완료한 일이 동기화 후 맥에서 다시 할 일로 나오지 않는다. 다시 보기 변경이 치과 예약 시각을 바꾸지 않는다. 완료·보관·삭제를 모두 되돌릴 수 있다.

근거: [NowBand.swift](../../../ios/LazyMemo/NowBand.swift), [Memo.swift](../../../Sources/LazyMemoCore/Model/Memo.swift), [RecallViews.swift](../../../Sources/LazyMemoReminders/RecallViews.swift).

### 6. ‘지금 세 장’은 좋은 표면이지만 전체를 보장하지 않는다

**확인:** 최대 3개이며 다가오는 시각이 지난 시각보다 먼저다. 날짜 없는 메모는 고정하지 않으면 이 선정에 들어오지 않는다. 검색·폴더 필터 중에는 ‘지금’이 숨겨진다. 전체 목록은 별도로 유지된다.

**가설:** 사용자는 ‘지금’을 처리할 일 전체로 오해할 수 있다. 날짜도 고정도 하지 않은 ‘견적 보내기’는 앱이 챙겨 주지 못한다. 반대로 고정 자료는 반복 등장해 화면을 차지한다.

**변경:** 세 장은 유지하되 ‘놓친 것 2 · 오늘 4 · 나중에 7’처럼 전체로 가는 요약을 제공한다. 세 장을 고른 이유를 남긴다. 날짜 없는 메모를 AI가 임의의 할 일로 만들지 않고 저장 후 선택적 ‘나중에 다시 보기’를 준다. 미처리 오래된 항목은 한 번의 조용한 정리 제안으로 묶는다.

**통과 조건:** 항목이 20개여도 중요한 미처리 내용까지 두 번 이내의 조작으로 접근한다. 같은 오래된 메모를 매일 자동 알림으로 괴롭히지 않는다.

### 7. 빠른 입력 뒤의 되물음이 다음 입력을 붙잡는다

**확인:** 길찾기 질문은 설정값이 없으면 활성화된다. 시간·장소가 있는 약속 저장 뒤 출발지를 묻고, 대기 중 입력은 다음 새 메모보다 경로 답변으로 먼저 처리된다. 건너뛰기는 있지만 그 선택도 사용자의 일이다.

**사용자 장면:** ‘내일 3시 치과 @강남역’을 남긴 직후 ‘우유 사기’를 연속 입력하려는데 상자는 출발지를 기다리고 있다. 저장은 됐어도 다음 기록 흐름이 끊길 수 있다.

**변경:** 저장을 마치면 입력칸을 항상 다음 메모에 돌려준다. 저장 결과 옆에 ‘가는 길 보기’를 보조 행동으로 놓고, 선택한 경우에만 별도 흐름을 연다. 시간 미정 약속도 우선 저장하고 ‘시간 정하기’를 나중에 제안한다. 기존 대화형 입력을 선호하는 사용자는 옵션으로 유지할 수 있다.

**통과 조건:** 날짜·장소가 섞인 메모 5개를 연속으로 적을 때 새 문장이 앞 메모의 답변으로 소비되지 않는다.

근거: [RoutePlanner.swift](../../../Sources/LazyMemoPlaces/RoutePlanner.swift), 위 두 입력 모델.

### 8. 맥·폰 동기화는 파일 보존 외에 충돌을 이해시키는 경험이 필요하다

**확인:** 충돌 시 최신 `updated` 판본을 유지하고 다른 판본은 새 ID로 휴지통에 보존한다. 파일 쓰기는 원자적이지만 파일 조정 미적용이 보류 사항으로 남아 있다. 두 내용의 의미를 합치지는 않는다.

**사용자 장면:** 맥에서 회의 결론을 쓰고 오프라인 폰에서 할 일을 덧붙였다. 재연결 후 한쪽 문장은 본문에서 사라지고 휴지통에 있다. 복구 가능하더라도 사용자에게는 ‘동기화가 글을 날렸다’로 보일 수 있다. 실제 유실을 관찰한 것은 아니다.

**변경:** 충돌본을 일반 삭제물과 분리해 ‘다른 기기의 변경이 있어요’로 알려 주고 두 판을 나란히 보거나 둘 다 유지하게 한다. ‘이 기기에 저장됨’과 ‘다른 기기 반영 확인됨’을 혼동하지 않는다. 관찰할 수 없는 원격 완료를 초록 체크로 표시하지 않는다. 앱·위젯·확장 사이의 파일 조정과 충돌 보호를 먼저 검증한 뒤 자동 병합을 검토한다.

**통과 조건:** 두 기기 오프라인 동시 편집·체크박스 변경·사진 첨부 후 양쪽 내용이 복구 가능하고 충돌 위치를 쉽게 찾는다. 파일 조정만으로 모든 충돌이 해결된다고 간주하지 않는다.

근거: [ConflictSettlement.swift](../../../Sources/LazyMemoCore/Storage/ConflictSettlement.swift), [MemoVault.swift](../../../Sources/LazyMemoCore/Storage/MemoVault.swift).

### 9. 첫 경험은 기능 설명보다 ‘내 것이 안전하게 남았다’가 먼저여야 한다

**확인:** 맥과 폰 안내는 각 5단계이며 건너뛰기가 있다. 맥 앞부분의 연습 입력은 실제 메모로 저장하지 않는다. 캡처 초안은 일반 메모와 다른 로컬 파일로 보존한다. `CaptureDraftStore.flush`의 쓰기 실패는 호출자에게 노출하지 않고 실행 중 메모리에 남긴다.

**가설:** ‘저장 버튼이 없다’, ‘닫아도 남는다’는 말과 별도의 ‘남기기’ 확정·저장되지 않는 연습·동기화되지 않는 초안의 차이를 처음부터 이해하기 어렵다. 저장 공간 부족 뒤 종료 같은 경우에는 초안 복원 약속도 깨질 수 있다.

**변경:** 처음에는 실제 입력칸으로 시작하고 자기 메모 한 개를 진짜 저장한다. 저장 뒤 날짜 해석·취소·다시 보기 중 그 메모에 필요한 하나만 안내한다. 초안은 ‘작성 중 · 이 기기에 보관’, 확정은 ‘메모에 남김’으로 구분한다. 초안 쓰기 실패도 가볍지만 명확하게 표시한다. 기존 5장 안내는 도움말로 유지한다.

**통과 조건:** 처음 온 사람이 설명 없이 30초 안에 자기 메모를 저장하고 다시 찾는다. 저장 실패 주입 뒤 초안을 잃지 않도록 재시도·복사할 수 있다. 튜토리얼에 적은 내용을 다시 입력하지 않는다.

근거: [WelcomeWindow.swift](../../../Sources/LazyMemoUI/WelcomeWindow.swift), [TutorialView.swift](../../../ios/LazyMemo/TutorialView.swift), [CaptureDraftStore.swift](../../../Sources/LazyMemoCore/Storage/CaptureDraftStore.swift).

### 10. AI의 비용과 품질은 첫 효용을 떠받치기에 아직 검증이 부족하다

**확인:** 기본 후보 모델 manifest는 약 2.59GB 파일이다. 9월 15일 M4 Pro 개발 기기 보고서에서 질문 답변은 21/24로 자체 목표 95%에 미달했다. 같은 표에서 명령 20개는 전부 모델 없이 처리됐다. 이는 과거의 작은 평가이며 최신 품질 또는 실제 사용자 정확도로 일반화할 수 없다. M1 8GB·iPhone 15 Pro 검증은 플래너상 미완이다.

**변경:** 첫날은 모델 없이 입력·날짜·검색·다시 보기·완료가 전부 동작하게 한다. AI는 충분히 메모가 쌓인 뒤 선택적으로 ‘내 메모에서 근거 찾기’에 집중한다. 첫 답은 관련 원문 카드로 즉시 주고, 생성 문장은 뒤따르게 한다. 근거 충돌은 하나로 단정하지 않고 두 내용을 보여 준다. 웹 검색·일반 비서·여러 모델 선택은 기본 화면에서 뒤로 보낸다.

**통과 조건:** 모델 없이도 핵심 시나리오가 완결된다. 최소 지원 기기에서 답 정확도·취소·메모리·잠금 복귀를 다시 평가한다. 앱이 알고 있는 규칙으로 처리되는 동작을 위해 대용량 모델 설치를 요구하지 않는다.

근거: [ModelManifest.swift](../../../Sources/LazyMemoAssistant/ModelManifest.swift), [기존 앱 검색 벤치](../../../docs/research/local-model-benchmark-2026-09-15-app-retrieval.md), [구현 명세](../../../docs/JARVIS_IMPLEMENTATION.md).

### 11. 폰에서 흔히 생기는 자료를 받아들이는 폭이 좁다

**확인:** 현재 공유 확장 입력 수집은 plain text·URL을 처리한다. 이미지 데이터를 받아 OCR하는 경로는 이 구현에 없다. 기존 메모의 사진 표시와는 별개의 문제다.

**제안:** 핵심 신뢰 문제를 고친 뒤, 스크린샷 공유 → 원본 보존 → 선택적 텍스트 인식 → 날짜·시간 제안 → 다시 보기를 연결한다. 사진에서 읽은 숫자나 시각은 제안으로 표시하고 원본을 항상 열 수 있게 한다. 처음부터 모든 문서·PDF·음성·웹 페이지를 수집하려고 넓히지 않는다.

**매력의 장면:** 채팅 속 예약 스크린샷을 보내 두면 다음 날 예약 번호·주소·원본이 함께 나온다. 사용자가 이미 가진 정보를 다시 타이핑하지 않는 것이 가치다. 날짜 오인식 시 확인 없이 알림을 만들지 않는다.

**통과 조건:** 실제 한국어 예약·배송·행사 스크린샷으로 숫자·날짜 정확도를 평가하고, 인식 실패해도 원본 저장은 성공한다.

## 이미 있는 장점과 유지할 것

- 가입 없이 파일을 소유하고, 원문을 꺼낼 수 있다. 새로운 서버 계정이나 강제 클라우드로 바꾸지 않는다.
- 전역 캡처, 한국어 날짜 인식, 초성 검색, 공유 입력, Siri·App Intents, 위젯이라는 접근 경로가 있다. 없는 기능처럼 다시 제안하지 않는다.
- 알림의 미루기·다시 보기 칩 즉시 저장·폰 목록 미루기·설정 창·대화형 위젯은 이미 개선됐다. 9월 17일 감사의 미완 목록을 그대로 복사하면 현재와 어긋난다.
- 바탕화면 종이와 따뜻한 시각 스타일은 정체성으로 남긴다. 다만 바탕화면에 보이는 것만으로 놓친 일이 전달됐다고 판단하지 않는다.
- AI 변경 전 제안·근거·조건부 저장, 삭제의 휴지통 복구는 신뢰의 토대다. 단순화하면서 없애지 않는다.

## 후보 해결 방안

### 방안 A — 가장 빠르고 예쁜 바탕화면 메모 {#opt-desktop}

Mac 중심으로 입력·핀·검색·종이·서랍만 선명하게 만든다. AI·길찾기·복잡한 알림은 선택 기능으로 둔다. 구현 범위가 가장 작고 즉시 이해하기 쉽다. 반면 다시 사용할 이유가 사용자의 습관에 많이 의존하고, 폰과 알림에 투자한 강점을 충분히 쓰기 어렵다. 사용자들이 ‘늘 보이는 포스트잇’만 원한다는 관찰이 나오면 좋은 대안이다.

### 방안 B — 적은 것을 놓치지 않게 돕는 메모 {#opt-recall}

기록 → 필요할 때 다시 보기 → 원문 확인 → 완료/미루기를 한 흐름으로 완성한다. 지금 세 장·캡처·위젯·달력·파일 보존을 대부분 재사용할 수 있다. 완료/보관/미확인의 의미와 기기 간 동작을 정비해야 하므로 중간 이상의 비용이다. 매력은 기능 시연이 아니라 ‘이 앱 덕분에 처리했다’는 결과로 입증할 수 있다. **내 추천이다.**

### 방안 C — 로컬 AI 개인 비서 {#opt-assistant}

질문·명령·웹·교통·브리핑을 중심으로 확장한다. 잘 작동하면 인상적이지만 모델 다운로드·지원 기기·정확도·입력 의도 충돌·외부 서비스 안정성을 동시에 해결해야 한다. 현재 최소 기기 검증과 답변 품질 근거가 부족해 가장 큰 비용과 불확실성이 있다. B의 신뢰와 반복 사용을 확인한 뒤, 명확한 효용이 있는 기능만 단계적으로 채택한다.

## 추천 제품 경험

### 첫 대상과 한 문장

첫 대상 가설은 **맥으로 일하고 아이폰으로 약속·링크·짧은 할 일을 받지만, 기록한 것을 다시 찾거나 처리하는 데 자주 실패하는 사람**이다. ‘게으른 모든 사람’보다 관찰할 상황이 구체적이다. 기존 메모 앱 전체 이사를 요구하지 않는다.

제품 약속 제안: **“일단 남기세요. 다시 볼 때, 할 일과 원문이 같이 옵니다.”** ‘잊어도 된다’는 절대적 표현은 알림·미처리·동기화 검증이 뒷받침될 때만 쓴다.

### 세 장면으로 제품을 설명한다

| 장면 | 입력 | 다시 만나는 순간 | 끝내는 행동 |
|---|---|---|---|
| 작업 중 생각난 일 | 단축키로 ‘내일 견적 보내기’ 저장 | 오늘 항목과 필요 시 사용자가 정한 알림 | 완료 또는 다시 보기 |
| 폰으로 받은 약속 | 날짜와 링크를 공유, 이후 스크린샷 지원 | 예약 시각·주소·원본을 한 카드로 | 원문 열기/지도 열기 |
| 미뤄 둔 자료 | 링크를 저장하고 ‘주말에’ 선택 | 사용자가 고른 시점에 제목·원문 등장 | 읽고 보관 또는 미루기 |

여기서 ‘주말에’의 정확한 날·시각은 선택 결과로 보여 준다. 모델이 몰래 정하지 않는다. 상황별 알림 성공을 먼저 확인하고 영상이나 문구로 약속한다.

### 화면과 동작

- **입력:** 하나의 칸, 기본 행동은 저장. 날짜 해석은 수정 가능한 칩. 질문/명령은 보조 제안. 확정 뒤 ‘저장됨 · 내일 15:00 이 기기 알림’과 되돌리기가 보인다.
- **지금:** 최대 세 장과 전체 항목 요약. 각 카드에는 나온 이유, 원문/출처, 다음 행동을 둔다. 미처리는 자정을 넘어도 접근 가능하다.
- **맥:** 기존 캡처 창과 메뉴바에 같은 ‘지금’으로 가는 길을 제공한다. 종이는 선택적 표시 방식으로 유지한다. 전용 거대 대시보드를 새로 만들 필요는 없다.
- **아이폰:** 입력과 지금을 가까이 둔다. 위젯의 완료·미루기는 앱과 동일한 규칙을 쓴다. 새 제스처 암기보다 눈에 보이는 행동을 우선한다.
- **찾기:** 초성·키워드 결과와 원문이 기본이다. ‘지난주 받은 예약 링크’ 같은 문맥 찾기는 별도 평가 후 개선한다. AI가 실패해도 원문 목록은 남는다.

### 반드시 분리할 내부 의미

| 의미 | 제안 원칙 |
|---|---|
| 기록 원문 | 사용자 글·이미지·링크는 보존. 날짜 인식 결과와 구별 |
| 실제 일정 | 약속·마감 시점. 다시 보기를 미뤄도 변경하지 않음 |
| 다시 볼 시점 | 사용자가 이 기록을 다시 만날 시점 |
| 완료 | 사용자 의사, 기기 간 동기화, 되돌리기 가능 |
| 보관 | 필요시 검색 가능, 자동 완료로 취급하지 않음 |
| 오늘 숨김 | 제한된 표시 상태. 완료라고 표현하지 않음 |
| 예약 상태 | 현재 기기에서 관찰한 OS 예약 결과만 표시 |

이는 새 데이터 모델 제안이며 현행 구현 설명이 아니다. 기존 마크다운 파일은 읽을 수 있게 확장하고, `tidied`를 일괄 완료로 변환하지 않는다. 과거 파일에 사용자의 완료 의사가 없기 때문이다.

## 비슷한 제품에서 확인한 기준

2026-09-22 공식 문서를 확인했다. 비교 목적은 기능 수 경쟁이 아니라 사용자의 기대 기준이다.

| 기준 | 공식 문서에서 확인한 점 | LazyMemo에 적용할 판단 |
|---|---|---|
| [Drafts 시작 경험](https://docs.getdrafts.com/gettingstarted/) | 앱이 편집기로 바로 시작하고 기록 뒤 행동을 제공 | 첫 입력을 저장되지 않는 연습 대신 실제 기록으로 |
| [Apple Reminders 알림 설정](https://support.apple.com/en-by/guide/iphone/f898416824ef/ios) | 날짜만 있는 항목에 대한 알림 시간 설정 제공 | 날짜만 해석했을 때 알림 여부를 명확히 설명하고 선택권 제공 |
| [Apple Mail 다시 알림](https://support.apple.com/en-gb/guide/icloud/mm08b662fdaf/icloud) | 선택한 시각에 원래 메일을 다시 위로 올림 | 요약만 전달하지 말고 사용자가 행동할 원문을 함께 꺼내기 |

따라서 ‘빨리 입력한다’ 또는 ‘알림이 있다’만으로 독자적인 선택 이유가 충분하다고 보기는 어렵다. **분류 없이 받은 기록을, 믿을 수 있게 다시 꺼내 주고, 그 자리에서 끝내는 연결**을 제품의 검증 대상으로 삼는다. 차별성이 시장에서 입증됐다는 뜻은 아니다.

## 실행 우선순위와 통과 기준

일정 추정은 코드 검토에 근거한 초안이다. 실제 일정은 결함 재현·기기 확보·기존 파일 호환성 검토 뒤 확정한다. 2026-09-22 사용자가 조사·의견대로 구현하기로 승인했다. 실행 순서와 통과 조건은 [구현 인계서](../../../docs/PRODUCT_IMPLEMENTATION_HANDOFF.md), 진척은 `lazymemo-product-value` 플랜을 따른다.

| 순서 | 작업 묶음 | 먼저 확인할 증거 | 대략적 범위 |
|---|---|---|---|
| P0 | 미래 다시 보기/자동 정리 충돌, 복원 후 재정리, 초안 실패 가시성 | 현재 소스로 실패 재현 후 회귀 통과 | 수일, 재현 결과에 따라 변경 |
| P0 | 저장과 예약 결과 표시, 입력 경로별 알림 | 폰 잠금·종료·공유·다른 기기 수정 실기기 표 | 수일~1주, 기기 필요 |
| P1 | 언제나 저장 가능한 입력, 길찾기 질문 분리, 실제 첫 메모 | 신규 사용자 5명이 연속 입력과 복원을 설명 없이 수행 | 약 1주 |
| P1 | 미처리·완료·보관·숨김 정책, 지금 요약, 기기 간 완료 | 자정·반복·동시 수정·기존 파일 호환 회귀 | 약 1~2주, 가장 큰 설계 작업 |
| P2 | 스크린샷 공유와 선택적 OCR, 출처 포함 카드 | 실제 자료에서 원본 보존·숫자·날짜 검증 | 약 1~2주, 별도 기술 확인 |
| 이후 | AI 근거 찾기와 기기별 최적화 | 기본 경험 재사용과 최소 기기 품질 게이트 | 앞 단계 결과로 재산정 |

첫 구현 범위를 1~4번 진단에 집중한다. 테마 추가, 새 애니메이션, 웹 비서 범위 확대, 경로 탐색 고도화, 모델 선택지 확대는 일단 후순위로 둔다. 현재 기능을 무조건 삭제하자는 뜻은 아니다. 이미 쓰는 기능은 보존하면서 기본 사용 흐름에서 차지하는 비중을 줄인다.

## 사용자 검증 설계

**1차: 5명, 30분 관찰.** 개발자가 설명하지 않고 실제 메모 저장·질문형 문장 저장·미루기·완료·다시 찾기를 수행하게 한다. 앱을 아는 지인만으로 구성하지 않는다. 중단 지점과 잘못 예상한 결과를 기록한다. 30초 안에 첫 실제 메모, 실수한 동작을 바로 되돌리기, ‘지금’에서 항목을 찾는 과정을 본다.

**2차: 10명, 7일.** 기존 `recall-field` 계획을 활용한다. 별도 중복 플랜 대신 그 검증에 이번 시나리오를 반영한다. 메모 본문을 자동 수집하지 않고 동의한 참여자의 짧은 응답과 집계로 평가한다.

| 지표 | 시험용 통과 기준 | 주의 |
|---|---|---|
| 첫 효용 | 10명 중 8명 이상이 도움 없이 자기 메모 저장·재발견 | 튜토리얼 완주율로 대체하지 않음 |
| 실제 도움 | 7명 이상이 ‘놓칠 일을 처리했다’는 구체적 사례 1개 이상 | 단순 호감·예쁜 디자인 평가와 분리 |
| 재사용 | 5명 이상이 마지막 이틀에도 자발적으로 사용 | 독촉 직후 실행은 별도 기록 |
| 신뢰 | 재현 가능한 유실·미래 다시 보기 취소·완료 재등장 결함 0 | 작은 표본이 무결함을 증명하지는 않음 |
| 방해 | 불필요한 질문·알림 사례를 유형별 기록 | 평균 만족도에 묻지 않음 |

기준은 출시 성공 예측이나 업계 평균이 아니라 이 실험의 진행 판단선이다. 미달하면 곧바로 기능을 더하지 않고 입력·다시 보기·처리 중 어느 단계가 실패했는지 나눈다. 기록은 잘하지만 다시 보기 필요성을 못 느낀다면 A로 좁힌다. 다시 보기 덕분에 실제 일을 끝내면 B를 강화한다. 자연어 검색 요구가 반복될 때 C의 일부를 올린다.

## 결론

**추천은 B다.** LazyMemo가 더 매력적이려면 AI가 할 수 있는 일을 늘리는 것보다, 사용자가 아무 생각 없이 남긴 한 줄을 **안전하게 받아 두고 → 놓치지 않게 다시 꺼내고 → 그 자리에서 끝낼 수 있게** 해야 한다. 현재 자산 대부분은 이미 이 방향에 맞는다. 우선 바꿀 것은 기능 개수가 아니라 입력과 정리의 규칙, 알림의 신뢰, 완료의 의미다.

2026-09-22 사용자가 “너의 조사와 의견대로 구현할거야”라고 승인하여 B 방향을 채택했다. 이 토의는 `resolved`로 닫고, [구현 인계서](../../../docs/PRODUCT_IMPLEMENTATION_HANDOFF.md)와 `lazymemo-product-value` 플랜으로 넘긴다. 사용자 수요·실기기 검증은 여전히 미완이며 제품 코드는 이번 조사·인계에서 수정하지 않았다.
