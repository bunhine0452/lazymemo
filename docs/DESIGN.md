# lazymemo 설계문서

> 상태: v1 구현 반영 · 2026-08-28 · 근거: [`.oculpm/discussion/lazymemo-계획서/discussion.md`](../.oculpm/discussion/lazymemo-계획서/discussion.md) (resolved) · 실행 계획: [`.oculpm/planner/lazymemo-v1.md`](../.oculpm/planner/lazymemo-v1.md)

## 1. 개요

lazymemo 는 macOS 바탕화면에 상주하는 메모 + 캘린더 앱이다.

철학은 **"사용자는 게으르다"** 를 전제로 삼는 것이다. 게으름을 고치라고 요구하지 않고, 게으른 채로도 기록이 남게 만든다. 설계상 이는 두 가지 제약으로 번역된다.

1. **마찰 제거** — 앱을 "열어서" 쓰지 않는다. 메모는 항상 바탕화면에 떠 있고, 새 메모는 전역 단축키 한 번으로 시작되며, 저장 버튼은 존재하지 않는다.
2. **정리를 대신 해준다** — 사용자가 "다음 주 화요일에 치과" 라고 말하면 LLM 이 알아서 입력·분류·정리한다. 사용자가 구조를 유지할 필요가 없다.

여기에 두 개의 비기능 요구가 동등한 무게로 붙는다: **메모리를 최소로 쓸 것**, 그리고 **아마추어처럼 보이지 않을 것**. 이 둘이 동시에 걸려 있다는 점이 아래 모든 기술 결정을 지배한다.

## 2. 확정된 결정

| # | 축 | 결정 | 핵심 근거 |
|---|---|---|---|
| D1 | 프레임워크 | **네이티브 SwiftUI + AppKit** | 메모리·Liquid Glass·SF Symbols·한글 IME 를 동시에 만족하는 유일한 선택. 웹뷰는 창당 메모리와 디자인 재구현 비용을 모두 떠안는다 |
| D2 | 창 구조 | **메모당 NSWindow** | 네이티브에서 창당 비용이 싸고 드래그·리사이즈·z-order·접근성을 OS 가 처리한다 |
| D3 | LLM 경로 | **lazymemo 가 MCP 서버** (1차) | Claude Desktop 연동은 이 방향만 성립한다. API 키 불필요, 토큰은 사용자 구독 부담 |
| D4 | 저장 | **마크다운 파일 정본 + SQLite 파생 인덱스** | 사용자가 직접 열람·이동 가능, MCP 연동이 거의 공짜, 동기화는 폴더 위치로 해결 |
| D5 | 캘린더 | **자체 뷰 우선**, EventKit 은 읽기 전용으로 후순위 | 의존성·권한 0 으로 시작. LLM 이 사용자의 실제 캘린더를 지우는 경로를 처음부터 열지 않는다 |
| D6 | 삭제 | **하드 삭제 금지**, trash 이동 + 보존 기간 | LLM 이 자율 삭제하므로 되돌리기가 선택이 아니라 필수다 |
| D7 | 배포 | **소스 빌드 + Homebrew cask** (오픈소스) | 둘 다 공증 없이 가능. 소스 빌드에는 검역 딱지가 애초에 안 붙고, cask 는 설치 뒤 떼어 낸다 — 미봉책이며 공증을 받는 즉시 지운다 (§12.2) |

각 결정의 기각된 대안과 전체 논거는 discussion 문서의 `{#opt-a}`~`{#opt-i}` 에 있다.

## 3. 검증된 기술 전제

아래는 추정이 아니라 2026-08-28 이 개발 머신(macOS 26.5.2, SDK 26.5, Xcode 미설치)에서 **실제로 빌드·실행해 확인**한 결과다. D1 은 이 검증 위에 서 있다.

| 전제 | 검증 방법 | 결과 |
|---|---|---|
| Xcode 없이 빌드 가능 | `swift build` (CommandLineTools만, tools-version 6.2) | ✅ 32.57초 |
| Liquid Glass 사용 가능 | SwiftUI `.glassEffect()` 컴파일 | ✅ SDK 26.5 에 존재 |
| 메뉴바 상주 | `NSStatusItem` + `NSImage(systemSymbolName:)` | ✅ |
| 바탕화면 레벨 창 | `NSWindow.level = CGWindowLevelForKey(.desktopIconWindow) + 1` | ✅ |
| Dock 아이콘 없는 상주 | `.accessory` + `LSUIElement` | ✅ |
| 유료 계정 없이 서명 | `codesign -s -` (ad-hoc) + 수동 `.app` 조립 | ✅ |
| 공증 없는 다운로드 배포 | quarantine 부여 후 `spctl -a -t exec` | ❌ `rejected` — 딱지가 붙어 있으면 안 열린다 (§12.2 가 이것을 떼어 낸다) |

마지막 항목이 핵심이다. Gatekeeper 거부는 **다운로드된 앱 번들**에 걸리는 것이라 Tauri·Electron 으로 만들어도 동일하다. 즉 공증은 프레임워크 선택 기준이 아니며, 로컬 빌드 산출물에는 `com.apple.quarantine` 이 붙지 않아 개발과 본인 사용에는 아무 제약이 없다.

## 4. 시스템 구조

**프로세스가 둘이다.** stdio MCP 는 클라이언트가 서버 프로세스를 띄우는 구조라, Claude Desktop 이 실행 중인 앱에 붙을 수 없다. 성립하는 형태는 `lazymemo-mcp` 라는 별도 실행 파일이 뜨고 **같은 Vault 를 직접 만지는** 것이다. D4(파일이 정본) 덕분에 두 프로세스의 계약이 파일 그 자체가 되어 이 구조가 거의 공짜다. 대가는 하나 — 앱이 외부 변경을 알아야 하므로 FSEvents 감시가 필요하다.

```
┌──────────────────┐         ┌─────────────────────────────────┐
│  Claude Desktop  │──stdio──▶  lazymemo-mcp  (별도 프로세스)   │
└──────────────────┘         │   └─ MemoTools → MemoService     │
                             └──────────────┬──────────────────┘
                                            │
┌───────────────────────────────────────────┼──────────────────┐
│  LazyMemo.app (LSUIElement, .accessory)   │                  │
│   ├─ MenuBarController   (NSStatusItem, 목록·최근 삭제)       │
│   ├─ QuickCapture        (전역 단축키 ⌥⌘N → NSPopover)        │
│   ├─ NoteWindowManager   (메모당 NSWindow, 레벨·Space·복원)   │
│   ├─ CalendarWindow      (바탕화면 캘린더 뷰)                 │
│   └─ MemoStore  (@MainActor, 관찰 가능)                       │
│         └─ VaultWatcher  (FSEvents — 바깥에서 온 변경 감지)   │
├───────────────────────────────────────────┼──────────────────┤
│  Domain — LazyMemoCore (AppKit 비의존)     ▼                  │
│   ├─ MemoService   ← 앱과 MCP 가 공유하는 유일한 규칙 지점     │
│   ├─ MemoVault     (파일 CRUD, trash)                         │
│   ├─ MemoIndex     (SQLite 파생 인덱스)                       │
│   └─ LayoutStore   (창 위치·크기·디스플레이)                  │
├──────────────────────────────────────────────────────────────┤
│  Storage                                                     │
│   ├─ Vault  : 마크다운 파일  ← 정본                           │
│   └─ Derived: index.sqlite, layout.json ← 재생성 가능          │
└──────────────────────────────────────────────────────────────┘
```

**단방향 원칙:** MCP 와 UI 는 모두 `MemoService` 를 통해서만 데이터를 건드린다. `MemoService` 는 항상 파일에 먼저 쓰고, 그 다음 인덱스에 변경을 통지한다. 인덱스는 절대 정본이 될 수 없다.

**규칙을 한 곳에만 둔다.** 앱과 MCP 가 각자 파일을 다루면 "삭제는 휴지통 이동뿐"(D6) 같은 약속이 두 번 구현되고, 한쪽만 고쳐지는 순간 깨진다. `MemoService` 가 그 단일 지점이다.

## 5. 데이터 설계

### 5.1 디렉터리 레이아웃

```
<Vault>/                          # 기본 ~/Documents/lazymemo (설정으로 이동 가능)
  notes/2026/08/<ulid>.md         # ← 정본. 사용자·LLM·동기화의 대상
  .trash/<ulid>.md                # 삭제 보존 (D6)

<App Support>/lazymemo/           # ← 전부 파생. 지워도 Vault 만 있으면 복원됨
  index.sqlite
  layout.json
  settings.json
```

**Vault 를 사용자 문서 영역에 두는 이유:** 사용자가 Finder 로 열어볼 수 있어야 잠금이 없고, 폴더를 iCloud Drive 로 옮기는 것만으로 동기화가 해결된다. 별도 백엔드를 만들지 않는다.

**그런데 앱에는 그 폴더를 따라갈 길이 없었다.** 위 문장과 README 는 처음부터 "옮기면 동기화가 된다"고 적어 두었는데, 옮긴 다음 앱을 켜면 기본 자리에 빈 폴더가 새로 생기고 화면에는 메모가 한 장도 없다 — **문서가 시킨 대로 한 사람이 전부 잃은 것으로 본다.** 「(설정으로 이동 가능)」은 오랫동안 코드에 없는 문장이었다. 지금은 있다 (`VaultRelocation`, 메뉴 → 설정 → 「메모 폴더 옮기기…」).

- **문이 하나다.** 「옮기기」와 「이미 옮긴 폴더 고르기」를 나눠 두면 사용자가 자기 상황을 먼저 판단해야 하는데, 그건 고른 자리를 보면 앱이 안다 — 거기 `notes/` 가 있으면 **그 폴더를 쓰고**(이미 옮겨 둔 사람), 없으면 지금 것을 **그리로 옮긴다**(이제 옮기려는 사람). 어느 쪽인지는 누르기 전에 글로 보여준다.
- **옮기는 것은 정본뿐이다.** 파생물(`index.sqlite`·`layout.json`·`settings.json`)은 언제나 Application Support 에 남는다 — 지워도 되는 것과 지우면 안 되는 것이 한 폴더에 섞이면 D4 의 "통째로 지워도 Vault 만 있으면 복원된다"가 깨진다. 덤으로 폴더를 알아야 설정을 읽고 설정을 읽어야 폴더를 아는 고리도 생기지 않는다 (`AppPaths.resolve`).
- **옮긴 뒤에는 앱을 껐다 켠다.** 저장소·인덱스·파일 감시자·떠 있는 창을 살아 있는 채로 갈아 끼우면 "반쯤 옛 자리를 보고 있는 상태"가 생기고, 저장 버튼이 없는 앱에서 그 상태는 곧 글을 잃는 자리다. 뜨는 데 1초가 안 걸리므로 껐다 켜는 편이 짧고 안전하다. 옮기기 **전에** 적던 글을 전부 파일에 내린다.
- **적어 둔 폴더가 없어졌으면**(외장 디스크를 안 꽂았거나 iCloud 가 아직 안 내려왔거나) 기본 자리로 돌아가되 **메뉴 첫머리에 그렇게 적는다.** 조용히 되돌아가면 사용자가 보는 것은 "메모가 전부 사라졌다"이다. 설정도 지우지 않는다 — 그 자리가 돌아오면 다시 그리로 간다.

**창 위치를 메모 파일이 아니라 `layout.json` 에 두는 이유:** 메모 파일은 사용자와 LLM 이 읽고 쓰는 대상이다. 창을 드래그할 때마다 정본 파일이 갱신되면 동기화 충돌과 무의미한 diff 가 생기고, LLM 이 파일을 다시 쓰면서 좌표를 날릴 위험이 있다. UI 상태는 기계 영역에 격리한다.

### 5.2 메모 파일 형식

```markdown
---
id: 01K3ZQ8F7N2R4M6X8B0V5T9WQY   # ULID (시간 정렬 가능)
created: 2026-08-28T16:29:50+09:00
updated: 2026-08-28T16:29:50+09:00
due: 2026-09-01                   # 선택 — 날짜만 (마감·목표)
at: 2026-09-01T14:00:00+09:00     # 선택 — 시각까지 (약속)
tags: [약속, 병원]
color: yellow
pinned: false
---
치과 예약 — 강남역 3번 출구
```

- 본문은 순수 마크다운. 앱이 없어도 읽힌다.
- `due` 와 `at` 이 캘린더 표시의 유일한 근거다. **둘 다 없으면 그냥 메모, 있으면 캘린더에도 나타난다.** 메모와 일정을 별도 타입으로 나누지 않는 것이 핵심 단순화다 — LLM 이 "약속"과 "목표"를 구분해 저장할 필요 없이 날짜 필드만 채우면 된다. 타입은 나누지 않되 **자리는 나뉜다**: 날짜가 붙은 것은 바탕화면에 종이로 내려앉지 않고 달력이 맡는다 (§7.2).
- 알 수 없는 frontmatter 키는 보존한다 (사용자가 직접 넣은 필드를 앱이 지우지 않는다).
- 휴지통에 있는 동안에는 `deleted:` 가 추가된다. 보존 기간 계산의 근거를 인덱스가 아니라 파일에 두어, 인덱스를 지워도 살아남게 한다.
- 시각은 **초 단위까지만** 적는다. 사람이 읽을 파일이기 때문이며, 그 대가로 모델도 초 미만 정밀도를 들고 있지 않는다 — 안 그러면 저장 직후 메모리와 디스크가 어긋난다.

### 5.3 파생 인덱스

`index.sqlite` 는 날짜 범위 쿼리와 전문 검색만 담당한다. 순수 파일 스캔으로는 캘린더의 "이번 달 일정" 쿼리가 메모 수에 비례해 느려지기 때문이다.

- 스키마: `memos(id, path, created, updated, due, at, color, pinned, mtime)` + `memos_fts(body)` (FTS5, `tokenize='trigram'`)
- **한국어 검색은 두 경로로 나뉜다.** `unicode61` 토크나이저는 한글 부분 일치를 못 하고, `trigram` 은 3글자 미만을 색인하지 않는다 (실측: `강남역`은 찾고 `남역`은 못 찾음). `병원`·`약속` 같은 두 글자 검색이 흔하므로 3글자 미만은 LIKE 스캔으로 떨어뜨린다.
- **불변식: 인덱스는 언제든 Vault 전체 스캔으로 재생성 가능해야 한다.** 인덱스에만 존재하는 정보를 만들지 않는다.
- 기동 시 파일 mtime 과 인덱스를 대조해 변경분만 갱신하고, 불일치가 감지되면 통째로 재생성한다.

## 6. 삭제와 되돌리기 (D6)

LLM 이 자율적으로 삭제하는 이상, 첫 오작동에 사용자 신뢰가 끝난다. 따라서 삭제 경로를 구조적으로 안전하게 만든다.

- `MemoStore.delete(id)` 는 **파일을 지우지 않는다.** `.trash/` 로 이동시키고 인덱스에서 내린다.
- 하드 삭제는 보존 기간 경과 후 앱이 수행하며, MCP 도구로는 **노출하지 않는다.** LLM 이 도달할 수 있는 코드 경로에 하드 삭제가 없다.
- `restore_memo` 로 되돌릴 수 있고, 메뉴바에 되돌리기 동선을 둔다. **방금 지운 것은 하위 메뉴에 접어 두지 않는다** — 잘못 눌렀다는 것을 아는 순간은 지운 직후이고, 그때 되돌리는 길이 한 겹 안에 있으면 조작이 둘로 늘어난다. 5분이 지난 것만 「지운 메모 N장」 아래로 내려간다.
- **지우는 길이 넷이다 — 종이 위, 메뉴 목록, 빠른 입력, 달력 줄.** 처음에는 오른쪽 버튼 메뉴 하나만 두었다. 겹쳐 뜨는 조작 줄에 휴지통을 놓으면 「치우기(×)」와 나란히 서서 잘못 누른다는 이유였다. 실제로 써 보니 **그 판단이 틀렸다.** 오른쪽 버튼 메뉴는 `NSTextView` 의 시스템 편집 메뉴(잘라내기·맞춤법·받아쓰기·서비스…)를 통째로 이고 있어서 「이 메모 지우기」가 그 맨 아래에 있었고, 메뉴바 목록에서는 아예 지울 수 없었다. **지울 길이 사실상 없는 것이 잘못 누르는 것보다 나쁘다.**
  - 종이 위: 겹쳐 뜨는 조작 줄의 **가장 왼쪽**에 붉은 휴지통. ×(치우기)는 오른쪽 끝에 그대로 두고 사이에 구분선을 세운다. 모서리로 뻗는 손이 지나가지 않는 자리이고, 색이 다르면 반쯤 보고도 갈린다.
  - 목록 위: 메뉴바 목록의 각 줄 오른쪽 끝. 자세한 것은 §14.10.
  - 빠른 입력의 목록 줄 오른쪽 끝 (§8). **메뉴 목록이 여덟 장에서 끊기므로 이것이 없으면 아홉 번째 메모부터는 지울 길이 없었다** — 넘친 것을 "빠른 입력에서 찾기" 로 넘겨 놓고, 정작 거기서는 열기만 됐다.
  - 달력 줄의 오른쪽 끝 (§10). **여기가 마지막까지 뚫려 있었다** — 「미루기」·「종이로」는 있는데 지우기만 없어서, 필요 없어진 일정을 치우려면 날짜를 떼어 바탕화면으로 내려보낸 뒤 그 종이를 찾아 지워야 했다. 조작이 셋이고, 그 사이 치우려던 것이 종이 한 장으로 눈앞에 난다. 「종이로」는 *언제 할지 모르겠다*는 뜻이고 지우기는 *안 하겠다*는 뜻이라, 둘을 한 버튼에 묶을 수도 없다.
  - 오른쪽 버튼 메뉴의 「이 메모 지우기」도 그대로 남는다. 다섯 다 같은 `MemoStore.delete` 로 간다.
- **되돌리는 줄은 지운 그 자리에 남는다.** 잘못 눌렀다는 것을 아는 순간은 지운 직후인데, 그때 되돌리는 길이 메뉴 안에만 있으면 지우기는 한 번이고 되돌리기는 셋이 된다 — 그런 휴지통은 못 누르는 버튼이다. 목록(빠른 입력)과 달력은 바로 아래 줄에, **종이는 그 창 위에** 8초 동안 「지웠습니다 · 되돌리기」를 든다. 종이만 오랫동안 예외였다: 창이 소리 없이 사라져 화면에 흔적이 한 줄도 안 남았다. 그동안 `layout.json` 이 그 메모의 자리를 곧바로 지워서 되살린 종이가 엉뚱한 곳에 떴는데, 지금은 휴지통에 있는 것의 자리도 함께 남긴다 — 되돌리기는 되돌리기여야 한다.
- **확인 대화상자를 띄우지 않는다.** 하드 삭제가 없는 이상 물어볼 것이 없다. 물어보는 순간 "게으른 채로 굴러간다"가 깨지고, 사람은 두 번째부터 읽지 않고 누른다 — 대화상자는 안전이 아니라 안전하다는 느낌만 준다. 안전은 되돌리기가 만든다.
- 파일 이동이라 비용이 사실상 0 이다 — 이 안전장치는 D4(파일 기반) 덕분에 싸게 얻어진다.

## 7. 창 시스템

메모 하나 = `NSWindow` 하나 (D2).

- `styleMask: .borderless`, `isOpaque = false`, `backgroundColor = .clear`, 내용은 `NSHostingView` 로 SwiftUI 부착
- `level = CGWindowLevelForKey(.desktopIconWindow) + 1` — 바탕화면 위, 일반 창 아래
- `collectionBehavior = [.canJoinAllSpaces, .stationary]` — Space 를 옮겨도 따라오고 Mission Control 에서 흔들리지 않는다
- `.resizable` 을 함께 준다 — 테두리가 없어도 가장자리 끌기가 살아난다
- 위치·크기는 디스플레이 UUID 와 함께 `layout.json` 에 저장. 복원 시 **어느 화면에도 닿지 않을 때만** 주 디스플레이 안으로 끌어온다. 사용자가 일부러 화면 밖으로 걸쳐 놓은 창은 건드리지 않는다
- **창을 닫는 것은 삭제가 아니라 숨김이다.** `layout.json` 의 `hidden` 으로 기록하고 메뉴에서 다시 연다
- **동시에 띄우는 창은 24개까지.** "메모는 항상 바탕화면에 있다"는 약속과 메모리 예산이 부딪히는 지점이고, LLM 이 한 번에 여러 장을 만들 수 있다. 넘치는 메모는 메뉴 목록에서 연다

**구현 함정:** `NSHostingView` 의 기본 `sizingOptions` 는 SwiftUI 뷰의 이상적 크기를 창에 반영한다. `sizingOptions = []` 로 끄고 `contentView` 를 붙인 **뒤에** `setFrame` 을 불러야 `layout.json` 이 정본이 된다. 그러지 않으면 창 크기 복원이 조용히 깨진다.

**이 영역이 프로젝트 최대 리스크다.** Stage Manager, Mission Control, "월페이퍼 클릭 시 데스크탑 표시", 전체화면 앱, 다중 디스플레이 연결/해제가 각각 창 레벨 동작을 바꿀 수 있고 문서화가 부족하다. 그래서 계획상 다른 기능보다 **먼저 스파이크**로 검증한다 (`{#window-spike}`).

### 7.1 조작 규칙 — 불편은 곧 실패다

lazymemo 의 사용성 기준은 하나다: **사용자가 조작에서 불편을 느끼는 순간 끝이다.** 바탕화면에 상주한다는 선택은 편안함을 공짜로 주지 않고, 오히려 보통 앱에는 없는 함정을 여럿 만든다. 아래 다섯 규칙이 그 함정을 메운다.

| 규칙 | 함정 | 구현 |
|---|---|---|
| **첫 클릭이 그대로 먹힌다** | 다른 앱을 쓰다 메모를 누르면 첫 클릭이 앱을 깨우는 데만 쓰이고 사라진다 — "눌렀는데 안 써진다" | `acceptsFirstMouse` (`MemoNSTextView`, `FirstMouseHostingView`) |
| **본문 어디를 끌어도 종이가 움직인다** | 본문이 창의 거의 전부를 `NSTextView` 로 덮어 `isMovableByWindowBackground` 가 영영 발화하지 않는다 — 메모를 옮길 방법이 없다 | 편집 중이 아니면 끌기를 `performDrag` 로 넘기고, 편집 중이라도 **글자 없는 자리**면 넘긴다. 끌지 않았으면 그 자리에 커서를 세운다 |
| **손이 닿은 종이는 앞으로 나온다** | 바탕화면 레벨 창은 브라우저 뒤에 있다. "메모 열기"가 화면상 아무 일도 일으키지 않으면서 키보드 포커스만 보이지 않는 곳으로 옮긴다 | 창 자리가 둘이다 — 평소 `desktopIconWindow+1`, 키를 잡은 동안 `floating-1`. `becomeKey`/`resignKey` 에서 오간다 |
| **포인터 반응은 앱이 뒤에 있어도 산다** | SwiftUI `.onHover` 는 키 윈도에서만 반응해, 철학 3·4(바래고 되살아나기, 겹쳐 뜨는 조작)가 실사용에서 통째로 죽는다 | `.activeAlways` 추적 영역 (`HoverSensor`) |
| **포커스는 빌리면 돌려준다** | 상주 앱은 상자를 띄우려 스스로 활성화한다. 그냥 숨기면 보이는 창 없이 앱이 활성으로 남아 다음 타자가 허공으로 간다 | 빠른 입력을 닫을 때 `NSApp.deactivate()` (메모를 열어 보여주는 경우만 예외) |

세 번째 규칙에서 `floating` 이 아니라 **`floating - 1`** 을 쓰는 이유: 메모를 고치는 중에 ⌥⌘N 을 눌렀을 때 빠른 입력 상자가 메모에 가리면 안 된다.

### 7.2 종이가 되는 것과 달력이 맡는 것

달력에서 「이 날에 적기」로 일정을 하나 넣을 때마다 바탕화면에 종이가 한 장씩 생겼다. 열 개를 넣으면 열 장이고, 창 24개 상한(§7)이 일정으로 채워져 정작 눈에 밟혀야 할 메모가 밀려난다. **원인은 달력이 아니었다** — 창 관리자가 "새 메모는 무조건 바탕화면"이었고, 그래서 빠른 입력도 MCP 도 결과가 같았다.

여기서 갈림길이 하나 나온다. 메모와 일정을 **타입으로 나누는 것**은 안 된다 — §5.2 의 핵심 단순화가 바로 그것이고, 나누는 순간 사용자가 적기도 전에 "이건 둘 중 뭐다"를 고르게 된다. 나눌 것은 타입이 아니라 **자리**다.

| 무엇 | 어디 | 왜 |
|---|---|---|
| 날짜 없음 | 바탕화면의 종이 | 언제 볼지 아직 정해지지 않았다. 정해지지 않은 것은 눈에 밟혀야 잊히지 않는다 |
| 날짜 있음 | 달력 | 언제 볼지 이미 정해졌다. 그 날이 오면 달력이 꺼내 준다 (철학 2 — 시간이 유일한 구조) |

**사용자가 고를 것이 하나도 없다.** 이미 치고 있는 글자가 결정한다 — "내일 3시 치과"라고 적었으면 그것은 일정이고, "우유"라고 적었으면 그것은 종이다. 모드도, 버튼 두 개도 두지 않는다 (§8 — 모드 전환이 없어야 조작 수가 준다).

규칙은 `NoteWindowManager.staysOnDesktop` **한 곳**에 있다. 메모가 태어나는 길이 셋(달력·빠른 입력·MCP)이라, 만드는 자리마다 "종이를 낼까 말까"를 적으면 셋 중 하나가 반드시 어긋난다 — 실제로 어긋나 있었다. 그리고 **사람이 한 번 정한 것은 언제나 이긴다**: `layout.json` 에 기록이 있으면 그 뜻을 따르므로, 달력에서 줄을 눌러 꺼낸 일정은 그대로 종이로 남는다. 이 규칙은 아무도 정한 적 없는 메모에만 말한다.

이 결정에 딸려 오는 것이 셋이다.

- **확인은 달력이 대신 한다.** §8 은 "확정한 메모는 잠깐 앞으로 나왔다 내려앉는다"로 "적히긴 한 건가"를 막았다. 일정에는 나올 종이가 없으므로 **달력이 같은 몸짓을 한다** — 그 날을 고르고 포커스를 뺏지 않은 채 잠깐 앞으로 나왔다 내려앉는다 (`riseBriefly`). 닫혀 있었으면 연다. 일정을 적었는데 받을 달력이 없으면 그 일정은 화면 어디에도 나타나지 않는다.
- **달력의 열림 여부도 복원 대상이 된다.** 일정이 보이는 자리가 달력뿐인 이상, 껐다 켤 때마다 달력이 사라지면 일정도 함께 사라진다. `layout.json` 의 `calendar` 키에 좌표와 나란히 남긴다.
- **어디로 가는지는 누르기 전에 보인다.** 빠른 입력의 날짜 칩이 「9월 1일 (월) 15:00 · 달력으로」라고 말한다. 적고 난 뒤에 알려 주면 그건 통보이고, 통보는 되돌릴 수 없다 — 칩이 떠 있는 동안에는 한 글자만 지우면 도로 종이가 된다. 칩에 있던 달력 아이콘은 낱말로 바꿨다. 아이콘은 "날짜다"까지만 말하고 "달력으로 간다"를 말하지 못한다 (§10.5 와 같은 이유).


### 7.3 자리를 옮기는 두 동사

§7.2 는 자리를 나눠 놓고 **옮길 수 없게** 해 두었다. 갈림길이 메모가 태어나는 순간에만 발화했기 때문이다 — 그 뒤로 날짜를 붙이거나 떼는 길은 앱 어디에도 없었고(날짜를 지우는 함수는 아무도 부르지 않은 채 남아 있다가 지워졌다 — 부를 자리가 없는 기능은 없는 기능이다), 설령 있었더라도 「사람이 정한 것이 이긴다」는 예외에 걸렸다 — 한 번 종이가 된 메모는 일정이 되어도 종이로 남았다.

실제로 사람이 달력에 하는 일을 세면(§10.1) 「미룬다·본다·넣는다」 옆에 하나가 더 있다. **자리를 바꾼다** — "이거 언제 할지 정했다" 와 "언제 할지 모르겠다" 는 게으른 사람에게 가장 자주 오는 두 생각이고, 둘 다 화면 밖에 있었다.

| 동사 | 어디서 | 무엇이 일어나는가 |
|---|---|---|
| **달력에 놓기** | 종이의 겹쳐 뜨는 조작 줄 (＋ 가 붙은 달력) | 달력이 열려 앞에 서고, 그 메모를 **들고** 놓을 날을 기다린다. 칸을 하나 누르면 그 날의 마감이 되고 종이는 물러난다 |
| **종이로** | 달력에서 포인터가 올라온 줄, 「미루기」 옆 | 날짜를 뗀다. 그 메모는 다시 그냥 메모가 되어 바탕화면에 종이로 나온다 |

**날짜를 묻는 상자를 띄우지 않는다.** 달력 위에서 날짜를 가리키는 방법은 이미 하나 있고(끌어다 놓기 — 자리로 가리킨다), 놓기는 그것과 같은 낱말을 쓴다. 다른 점은 집어 든 자리가 달력 밖이라는 것뿐이라, 들고 있는 동안 손끝을 따라다니는 조각도 끌 때와 **같은 조각**이다. 달력이 놓을 날을 기다리는 동안에는 창이 앞에 서 있는다 (`rise`) — `riseBriefly` 로는 안 된다. 겨누는 시간은 사람마다 다르고, 정해 둔 시간이 지나면 조준하던 판이 브라우저 뒤로 사라진다.

**종이를 실제로 옮기는 규칙은 한 곳에 있다** — `NoteWindowManager.handover(was:now:)`. 자리가 바뀌는 **그 순간에만** `layout.json` 의 `hidden` 을 다시 쓴다.

- 날짜를 얻었다 → `hidden = true` (달력이 맡는다)
- 날짜를 뗐다 → `hidden = false` (다시 눈에 밟혀야 한다)
- 그대로다 → 건드리지 않는다. 사람이 꺼내 둔 일정(§7.2 의 예외)이 그대로 남는다
- **처음 본 메모는 바뀐 것이 아니다.** 기동 직후 모든 일정을 한꺼번에 숨김으로 적으면, 일부러 꺼내 둔 일정이 껐다 켜는 것만으로 통째로 사라진다

여기 한 곳을 지나므로 **MCP 도 같다** — Claude 가 메모에 날짜를 붙이면 그 종이는 바탕화면에서 물러나고, 지우면 돌아온다. 세 길(달력·종이·MCP)에 각각 적었다면 하나는 반드시 어긋났을 것이고, §7.2 를 만든 결함이 정확히 그것이었다.

**돌아온 종이는 나왔다는 것을 스스로 말한다.** 바탕화면 레벨의 창은 브라우저 뒤에 나므로, 그냥 두면 「종이로」를 누른 사람에게는 아무 일도 일어나지 않은 것으로 보인다 (§7.1 의 셋째 규칙). 새로 적힌 메모와 같은 몸짓 — 잠깐 앞으로 나왔다 내려앉는다.

되돌리기는 달력의 그 줄이 그대로 맡는다 (§10.2). 다만 되돌릴 것이 셋이 되었으므로 낱말도 셋이다 (`MoveNote`) — 「8월 31일로 옮겼습니다」·「9월 1일에 놓았습니다」·「종이로 보냈습니다」. 하나로 뭉뚱그리면 방금 무엇이 어디로 갔는지를 화면에서 다시 찾아야 한다.

## 8. 빠른 입력

"게으름 타파"가 실제로 구현되는 지점이다.

- 전역 단축키 **⌥⌘N** → `NSPopover` 즉시 표시 → 커서 활성. **목표 150ms, 실측 중앙값 12.5ms.** 팝오버와 뷰를 앱 기동 시 미리 만들어 두고 표시만 토글하며, 애니메이션은 끈다.
- 단축키는 Carbon `RegisterEventHotKey` 로 등록한다. `CGEventTap` 은 손쉬운 사용 권한을 요구하는데, 첫 실행에서 사용자를 시스템 설정으로 보내면 "게으름 타파" 전제가 그 자리에서 무너진다. ⌘Space·⌃Space·⌃⌥Space 는 Spotlight 와 입력 소스 전환이 쓰므로 피했다.
- 한 상자가 **입력과 검색을 겸한다.** 치면 기존 메모가 걸러지고, 그대로 Return 이면 새 메모가 된다. 모드 전환이 없어야 조작 수가 준다.
- **빈 상자에도 목록이 있다 — 열면 요즘 메모가 아래에 놓인다.** 예전에는 한 글자라도 쳐야 목록이 나왔는데, 그러면 "무엇을 적어 뒀더라"를 확인하려는 사람이 기억해 낸 낱말을 먼저 대야 했다. 기억이 안 나서 여는 것인데도. 열면 바로 보이고, 치기 시작하면 그 자리가 찾은 것으로 바뀔 뿐 목록이 사라지지는 않는다. ↓ 한 번이면 목록으로 내려가고 ⌘⏎ 로 연다 — 메모를 다시 보려고 메뉴바 아이콘을 눌러 목록을 뒤지던 길이, 이 앱에서 가장 자주 하면서 가장 멀었다. 다섯 장까지만 얹는다(메뉴는 8장): 여기는 적는 자리가 먼저고, 목록이 길면 적을 자리가 화면 밖으로 밀린다. 줄의 생김새는 메뉴 목록과 **같은 낱말을 쓴다** (§14.10 — 찬 점 = 바탕화면에 있음, 빈 점 = 치워 둔 것, 오른쪽에 시간 한 조각). 포인터가 얹힌 줄이 곧 화살표로 고른 줄이라, 손과 키보드가 같은 것을 가리킨다.
- **목록에서 그 자리에서 지운다.** 줄 오른쪽 끝에 휴지통, 고른 줄에서는 ⌘⌫ — Finder 와 같은 손짓이라 여기서만 쓰는 규칙을 새로 배울 것이 없다. 메뉴 목록이 여덟 장에서 끊기므로 그 너머는 이 상자에서만 만나는데, 열기만 되고 지울 수 없으면 아홉 번째 메모부터는 바탕화면에서 그 종이를 찾아내는 수밖에 없었다. 지운 뒤 **상자는 닫지 않는다** — 치우려고 연 사람은 대개 한 장만 지우지 않고, 지울 때마다 닫히면 단축키를 다시 눌러 같은 낱말을 또 쳐야 한다. 고른 자리도 지킨다: 지운 줄의 다음 줄이 그 자리로 올라와, ⌘⌫ 를 연달아 누르면 위에서부터 훑으며 치워진다. 되돌리는 줄은 **목록 바로 아래에 남는다** (D6) — 잘못 눌렀다는 것을 아는 순간은 지운 직후인데, 그때 되돌리는 길이 메뉴 안에만 있으면 상자를 닫고 아이콘을 눌러 찾아 들어가야 한다. 힌트 줄에는 **⌘ 까지 적는다**(`⌘⌫ 지우기`) — ⌫ 하나는 글자를 지우는 키라, 그렇게만 적으면 사람은 글을 지우면서 메모가 안 지워진다고 여긴다. 휴지통은 평소 28% 세기로 늘 켜 두고 고른 줄에서 또렷해지며, 그 위에 포인터가 오면 붉은 원이 깔린다 (§14.10 과 같은 규칙).
- **끊긴 자리에 끊겼다고 적는다 — 그리고 넓어진다.** 다섯 줄에서 그냥 잘려 있으면 사람은 그것을 "이게 전부"로 읽고, 아홉 번째 메모는 있는 줄도 모르는 채 다시 적힌다. 목록 아래에 「… 외 N장 더」한 줄을 두고, 누르거나 **마지막 줄에서 ↓ 를 한 번 더** 누르면 스무 줄까지 넓어진다(마지막 줄의 ↓ 는 어차피 할 일이 없던 키다). 화면에 놓는 수와 **아는 수를 갈라 놓은 것**이 요점이다: 검색은 5줄이 아니라 200줄까지 세어 오므로 "몇 장이 남았는지"를 앱이 실제로 안다. 스무 줄로도 못 담으면 그때는 목록을 더 늘리지 않고 낱말로 좁히라고 적는다 — 스무 줄을 훑는 것보다 한 글자 더 치는 편이 짧다.
- 저장 버튼 없음. 입력이 멈추면 디바운스 후 자동 저장, 팝오버가 닫히면 즉시 flush.
- **Return 은 다음 줄로 간다.** 메모는 한 줄로 끝나지 않는다. 적기를 끝내는 것은 ⌘⏎ 다. 이 때문에 ↑↓ 가 글줄 이동과 찾은 목록 이동을 겸하게 되는데, **커서가 끝 줄에 닿았을 때만** 목록으로 넘어간다.
- **esc 로 닫아도 적던 글은 상자가 기억한다.** 버리면 여러 줄 적다가 손이 미끄러진 한 번에 전부 잃고, 반대로 닫을 때 저장해 버리면 — 이 상자는 검색을 겸하므로 — 메모를 찾으려고 친 낱말이 새 메모가 되어 쌓인다. 어느 쪽도 안 되므로 들고 있는다. 다시 열면 글이 전부 선택돼 있어 그냥 치면 덮어쓴다.
- **말풍선은 메뉴바 아이콘 밑에 매달린다.** 화면 한가운데 띄우던 것을 되돌렸다 — 단축키로 열든 아이콘을 누르든 같은 자리에서 열려야 사람이 "이 앱이 어디 있는지" 를 한 번만 배운다. 아이콘이 가려져 자리를 알 수 없을 때만 화면 위쪽으로 물러난다. 대가는 하나: 메뉴바가 붐벼 아이콘이 숨으면 매달 곳이 사라진다.
- **단축키는 바꿀 수 있다** (메뉴 → 설정). 목록에서 고르게 하지 않고 **누르면 그게 단축키다.** 다른 앱이 선점한 조합이면 등록이 실패하므로 그 자리에서 말해 주고 쓰던 것을 도로 걸어 둔다.
- **확정한 메모는 포커스를 뺏지 않는다.** 새 메모를 만들면 종이가 잠깐 앞으로 나왔다 스스로 내려앉고, 키보드는 사용자가 하던 앱에 그대로 있다. **날짜를 적었으면 나오는 것이 종이가 아니라 달력이다** (§7.2) — 그 메모는 종이로 남지 않으므로, 종이를 보여 주는 것은 거짓말이 된다. 활성화해 버리면 바탕화면 레벨의 **보이지 않는 창**으로 입력이 넘어가 이어서 친 글자가 사라진다. 반대로 아무 표시도 안 하면 "적히긴 한 건가"가 남는다 — 잠깐 보였다 내려앉는 것이 둘 다 피하는 유일한 길이다. 검색 결과를 골라 연 경우는 사용자가 "그 메모를 보자"고 한 것이므로 앞으로 데려온다.
- **Esc 는 손을 뗀다.** 편집을 끝내고 앱을 물러나게 해, 종이가 바탕화면으로 내려앉고 키보드가 원래 앱으로 돌아간다.
- 편집기는 `NSTextView` 기반. **한글 IME 조합을 OS 에 맡기는 것이 목적이며, 이는 D1 의 주요 근거 중 하나다.** 조합 중 상태를 가로채는 로직을 넣지 않는다.

**조합을 지키는 세 규칙** (`MemoTextSync`, 테스트로 고정):

1. `hasMarkedText()` 면 모델의 문자열을 되밀지 않는다 — 자모가 흩어진다.
2. 내용이 같아도 대입하지 않는다 — 대입만으로 선택 범위가 초기화된다.
3. 반영할 때 커서를 원래 자리로 되돌린다 — 안 그러면 문서 끝으로 튄다.

자동 저장도 조합 중에는 걸지 않는다. 그러지 않으면 파일에 `ㅊ` 같은 중간 자모가 저장된다.

### 8.1 메모장 — 줄머리 표시는 글자가 아니라 여백에 그린다

`- [ ] 우유` 를 치면 화면에는 **진짜 체크상자**가 보여야 한다. 그런데 정본이 마크다운이라(D4) 글자를 바꿔 끼울 수 없다 — 바꾸는 순간 파일도, 커서도, 되돌리기도, 한글 조합도 함께 어긋난다.

그래서 마커 글자(`- `, `- [x] `, `> `)는 **감추고**, 문단 들여쓰기로 비워 둔 왼쪽 여백에 `MemoNSTextView` 가 직접 그린다. 줄이 넘어가도 글이 가지런하고, 감춘 원문은 커서가 그 줄에 오면 되돌아와 고칠 수 있다.

**체크상자는 눌러서 뒤집는다.** 다 한 일을 알리려고 `[ ]` 를 `[x]` 로 글자를 고치게 하는 것은 이 앱이 가장 싫어하는 종류의 불편이다. 창에 포커스가 없어도 눌린다 — 바탕화면의 종이는 지나가다 툭 누르는 물건이다.

**여기서 세 번 틀렸고, 세 번 다 렌더를 눈으로 봐야만 드러났다.** 기록해 둔다.

| 틀린 것 | 증상 | 원인 |
|---|---|---|
| 줄 상자를 텍스트 컨테이너 좌표로 쓰고 여백을 안 더함 | 표시가 통째로 한 줄 위 | 컨테이너 좌표는 `textContainerInset` 만큼 어긋나 있다 |
| 눈높이를 라틴 글꼴의 x-높이로 계산 | 한글보다 낮게 앉음 | 한글에는 x-높이가 없고, 그리는 글꼴도 한글 대체 글꼴이라 지표를 믿을 수 없다 |
| 글꼴을 `NSTextView.font` 로 조회 | 계산이 통째로 0 | 그것은 **첫 글자의 글꼴**이고, 첫 줄이 `## 제목` 이면 감춘 `## `(0.01pt)를 물고 온다 |

세 번째가 특히 고약하다 — 빌드도 테스트도 통과하고 화면도 얼핏 멀쩡하다. 그래서 `LineMarkerTests` 로 좌표와 누르기를 못 박고, `render-ui.sh` 는 **실제 `NSTextView` 를 그대로 떠내** `editor.png` 로 낸다 (SwiftUI 대체 렌더로는 여백에 그리는 것을 볼 수 없다).

### 8.2 종이의 색 — 밝기를 맞추고 섞는다

색은 **바탕화면에 여러 장이 흩어졌을 때 서로 구별되는가**가 전부다. 한 장만 보면 어떤 세기든 그럴듯해 보이므로 여섯 색을 나란히 렌더해(`palette.png`) 정한다.

처음엔 잉크를 종이에 그대로 옅게 섞었는데, 그러면 **색마다 종이 밝기가 달라진다.** 파랑·보라는 어두워져 회색으로 죽고 노랑만 색으로 읽혔다 — 빛 모드에서 여섯 장이 사실상 같은 흰 종이였다. 색이 신원을 말하려면 잉크의 **밝기를 먼저 맞춘 뒤** 섞어야 한다.

- 채도는 곱해서 올리되 상한을 둔다. 무채는 낮은 채로 남아야 하고(색을 띠면 그건 무채가 아니다), 진한 색은 상한에서 멈춰야 문구점 형광 메모지로 넘어가지 않는다.
- 점 그리드도 잉크 색으로 찍는다. 종이를 어둡게 하지 않으면서 색을 더하는 값싼 방법이다.
- 나이가 들면 색도 함께 옅어진다 (철학 3).

**그 비율 한 벌을 두 외관이 함께 쓰고 있었다.** 빛 모드에서 고친 값을 그대로 어두운 종이에 대니 **같은 일이 다크에서 다시 일어났다** — 숯색 바탕에 26% 만 스민 색은 여섯 장이 전부 같은 숯색이고, 무채와 노랑의 거리가 빛 모드의 절반 이하였다. 어두운 종이는 색을 더 먹어야 색으로 보인다. 그래서 **스밈과 채도 상한과 밝기를 외관마다 따로 잡는다** (`PaperTint.light` / `.dark`).

눈으로는 "좀 비슷한가"까지밖에 말할 수 없어서 **재서 못 박았다** (`PaperPaletteTests`): 여섯 장에서 가장 닮은 두 장의 거리를 두 외관에서 각각 재고, 어두운 쪽이 밝은 쪽만큼 갈리는지 본다. 잉크 자체도 한 번 손봤다 — 보라와 파랑이 색상환에서 47° 밖에 안 떨어져 있어 늘 이 둘이 가장 닮은 쌍이었다. 종이에 스미면 채도가 절반 아래로 눌리므로 **잉크에서 미리 벌려 두어야 한다.**

**떠 있는 것은 바탕보다 밝다.** 빛은 위에서 오므로 종이 위에 뜬 조각(겹쳐 뜨는 조작 캡슐, 끌고 가는 일정 조각)은 바탕보다 밝아야 한다. 그 조각들을 맨 종이(`Paper.surface`)로 칠했더니 **어두운 쪽에서만 방향이 뒤집혔다** — 색이 스민 종이보다 맨 종이가 어두워서, 떠 있어야 할 조각이 파인 구멍으로 보였다. 그래서 조각은 제가 앉은 종이의 색을 그대로 들고 올라간다 (`PaperTint.raised`) — 재질은 하나이므로 떠 있는 것도 같은 종이의 한 조각이다. 그림자도 함께 뒤집힌다: 어두운 종이 위의 검은 그림자는 아무 일도 하지 않으므로 더 짙게 깐다.

같은 검사가 **글자 색에도 걸린다.** 면에 맞게 고른 색을 글자에 그대로 쓰면 한쪽 외관에서 읽히지 않는다 — 딥 네이비(`accent`)는 미색 종이에서 11:1 인데 숯색 종이에서는 1.6:1 로 바탕에 잠긴다. 「되돌리기」가 안 읽히면 그 줄은 있으나 마나다. 그래서 면을 칠하는 색과 글자로 쓰는 색을 갈라 둔다 — `accent`/`accentInk`, `danger`/`dangerInk`, `highlight`/`highlightInk`. 주말 숫자(일요일 빨강·토요일 파랑)도 어두운 종이에서는 밝은 쪽으로 올린다: 관행을 지키려던 색이 도리어 그 이틀을 가장 안 읽히는 칸으로 만들면 안 된다. 링크도 마찬가지였다 — 한 값으로 두었더니 숯색 종이에서 3.5:1 이라 본문 크기에 못 미쳤고, 빛 모드에서도 4.3:1 로 아슬아슬했다. **재는 자리는 맨 종이가 아니라 여섯 색 중 가장 불리한 종이다** — 링크는 어느 색 종이에도 붙는다.

**낮은 불투명도로 깐 면은 «면 색» 이 아니라 «잉크 색» 이다.** 놓을 자리를 가리키는 15% 판, 적는 줄의 밑줄, 단축키 칩의 바탕이 전부 딥 네이비를 옅게 깐 것이었는데 어두운 종이 위에서 아무것도 안 보였다. 끌고 있는 동안 가장 중요한 표시가 다크에서만 사라지는 셈이다. 종이 위에서 **읽혀야 하는 것**은 전부 잉크 쪽 값을 쓴다.

## 9. LLM 연동 (D3)

### 9.1 방향

Claude Desktop 은 외부 앱이 프롬프트를 보내고 결과를 받는 경로를 제공하지 않는다 (URL 스킴은 단방향, AppleScript 비활성 — 실측 확인). 성립하는 유일한 연동은 **lazymemo 가 MCP 서버가 되고 Claude Desktop 이 이를 호출**하는 방향이다.

부수 효과가 크다: API 키가 필요 없고 토큰 비용을 사용자 Claude 구독이 부담한다. 오픈소스 저장소에 키를 넣을 수 없다는 제약과도 맞아떨어진다.

### 9.2 도구 인터페이스 (초안)

| 도구 | 인자 | 비고 |
|---|---|---|
| `list_memos` | `query?`, `tag?`, `from?`, `to?`, `limit?` | 인덱스 경유 |
| `create_memo` | `text`, `due?`, `at?`, `tags?`, `color?` | 날짜 필드가 있으면 캘린더에도 반영 |
| `update_memo` | `id`, `text?`, `due?`, `at?`, `tags?` | 미지정 필드는 보존 |
| `delete_memo` | `id` | **trash 이동만.** 하드 삭제 아님 |
| `restore_memo` | `id` | trash 에서 복원 |
| `list_trash` | — | 휴지통 목록. `restore_memo` 에 넘길 id 를 얻는 유일한 길이라 추가했다 |

`update_memo` 는 넘기지 않은 필드를 보존하고, 빈 문자열을 넘기면 그 날짜를 지운다. 도구 인자 오류는 JSON-RPC 오류가 아니라 `isError: true` 결과로 돌려준다 — 모델이 읽고 스스로 고칠 수 있어야 하기 때문이다.

앱 내부 버튼으로 LLM 을 부르는 기능(F-2)은 후순위다. 필요해지면 `claude` CLI 서브프로세스 경로로 붙인다 — 사용자 구독 인증을 재사용할 수 있어 키 요구를 계속 피할 수 있다.

### 9.3 프라이버시

메모 본문이 외부로 나가는 경로는 MCP 연동뿐이며, 이는 사용자가 `claude_desktop_config.json` 에 직접 등록해야 활성화된다.

**네트워크를 쓰는 곳이 하나 더 생겼다 — 링크 카드**(`LinkPreviewStore`). 본문에 붙인 http(s) 주소의 제목과 그림을 가져오려고 그 주소에 접속한다. 이 절의 원래 문장은 "기본 상태에서 네트워크를 쓰지 않는다" 였고, 그 약속이 여기서 갈린다. 그래서 세 가지를 조건으로 붙였다.

1. **설정으로 끌 수 있고**, 끄면 접속 경로가 완전히 닫힌다 (`settings.json` 의 `embedsLinks`).
2. 나가는 것은 **주소 하나뿐이며 메모 본문이 아니다.** 다만 어느 사이트를 붙였는지는 그 사이트가 알게 되므로 README 에 그대로 적는다.
3. 한 번 가져온 것은 디스크에 남겨 **다시 묻지 않는다.** 실패한 주소도 그 세션 동안 다시 두드리지 않는다.

메뉴에서 이 항목에 "그 주소에 접속합니다" 를 함께 적는 이유가 이것이다 — 켜져 있다는 사실이 보이지 않으면 약속을 지킨 것이 아니다.

## 10. 캘린더 (D5) — 게으른 사람이 **조작하는** 달력

`due` / `at` 을 가진 메모가 캘린더에 나타난다 — 별도 이벤트 타입은 없다 (§5.2).

### 10.1 앞선 판을 버린 이유

한 판을 버리고 왔다. 「흐름」은 오늘부터 아래로 흐르는 목록이었고 조망은 상단의 점 스트립이 맡았다. 읽는 화면으로는 좋았지만 **조작이 하나도 없었다** — 할 수 있는 일이 스크롤과 메모 열기뿐이었다.

게으른 사람이 달력에 실제로 하는 일을 세어 보면 셋이다.

| 동사 | 빈도 | 앞선 판에서 |
|---|---|---|
| **미룬다** — "내일 하지 뭐" | 가장 잦다 | 없음. 메모를 열어 날짜를 고쳐야 했다 |
| **본다** — "다음에 뭐 있지" | 잦다 | 됐다 |
| **넣는다 / 옮긴다** | 보통 | 없음. 빠른 입력으로만, 옮기기는 아예 불가 |

셋 중 둘이 화면 밖에 있었다. "가장 자주 하는 일이 가장 멀다" 는 것은 조작 설계가 뒤집힌 것이고, 이 앱의 합격선(§7.1 — 불편은 곧 실패)에서는 그대로 실패다. **화면을 고친 것이 아니라 동사를 기준으로 다시 지었다.**

### 10.2 두 층 — 조망과 조작이 한 창에 있다

```
┌──────────────────────────┐
│ 7월  8월  9월      2026  │  머리 — 이웃 달의 이름이 곧 이동 버튼
│  일 월 화 수 목 금 토     │
│  …  …  …  …  …  …  …    │  달 격자 — 조망 + 놓는 자리
│          (28)            │  숫자 + 그 아래 번진 잉크(밀도)
│ ─────────╷────────────── │  접힌 자리 — 고른 날의 열을 가리킨다
│ 오늘 · 8월 28일 금요일    │  고른 날 — 조작 (여기부터는 적는 면)
│ ┃09:30 팀 회의   [미루기] │  ← 집어서 위 격자로 끈다
│ ┃      분리수거          │
│ 이 날에 적기 ┈┈┈┈┈┈┈┈┈┈ │  비워 둔 줄
│ 8월 31일로 옮겼습니다 되돌리기│
└──────────────────────────┘
```

두 층이 **한 창**에 있어야 "31일로 옮기기" 가 한 동작이 된다. 목록만 있으면 날짜를 글자로 쳐야 하고, 격자만 있으면 무엇을 옮기는지 가리킬 수 없다.

| 조작 | 어떻게 | 왜 그렇게 |
|---|---|---|
| 옮기기 | 아래 줄을 집어 위 칸에 놓는다 | 날짜를 말이 아니라 **자리**로 가리킨다 |
| 미루기 | 포인터가 올라온 줄에 겹쳐 뜨는 「미루기」 한 번 | 가장 잦은 일은 겨냥조차 필요 없어야 한다 |
| 적기 | 날을 고르고 그 자리에서 한 줄 | 상자를 따로 띄우지 않는다 |
| 되돌리기 | 옮긴 뒤 바닥에 8초간 남는 줄 | 끌기는 미끄러진다. 미끄러짐이 손실이 되면 안 쓰게 된다 |
| 종이로 | 「미루기」 옆에 함께 겹쳐 뜨는 「종이로」 | 날짜가 아니라 **자리**를 고친다. 미루기가 *언제*라면 이것은 *어디*다 (§7.3) |
| 열기 | 줄을 그냥 누른다 | 같은 제스처가 누르기와 끌기를 겸한다 (움직였으면 끌기) |

**규칙은 `LazyMemoCore` 에 있다** (`Schedule`). 옮기기는 `due` 와 `at` 을 **통째로** 다시 쓴다 — 한쪽만 건드리면 한 메모가 달력 두 칸에 서거나 시각이 사라진다. 미루기는 그냥 "+1일" 이 아니라 `max(그 일정의 다음 날, 내일)` 이다. 이미 지난 일정을 하루 미루면 **여전히 과거**라 아무것도 달라지지 않기 때문이다. 되돌리기가 한 줄로 끝나는 것도 이 덩어리 덕분이다 — 옮기기 전의 `Schedule` 을 그대로 되쓰면 된다.

### 10.3 낱말을 부품에서 펜 자국으로 바꿨다

동사는 맞게 서 있었는데 **생김새가 남의 것이었다.** 채운 원(오늘), 테두리 원(고른 날), 캡슐 점(밀도), `‹ ›`(달 이동), 1px 실선(두 층의 경계) — 전부 맞는 표시였고, 전부 **어느 앱에나 있는 표시**였다. 이 앱은 재질이 하나(§14.5 — 좋은 종이)인데 그 위에 놓인 표시만 UI 부품이면 달력만 남의 물건으로 읽힌다. 그래서 달력이 쓰는 낱말을 종이 위의 몸짓으로 다시 적었다 (`PenMarks.swift`).

| 뜻 | 버린 것 | 지금 | 왜 |
|---|---|---|---|
| 오늘 | 채운 노란 원 + 검은 숫자 | **손으로 그린 동그라미** + 안쪽에 스민 호박색 | 아이콘의 가변 굵기 흘림선과 같은 언어(§14.7). 채운 원 위에서는 잉크가 안 읽혀 숫자를 검게 바꿔야 했는데, 스민 색 위에서는 잉크가 그대로 산다 |
| 고른 날 | 회색 원 + 테두리 | **밑줄** | 종이에서 "지금 이걸 보고 있다"를 말하는 가장 오래된 몸짓. 동그라미와 겹치지 않아 오늘이면서 고른 날일 때도 둘 다 읽힌다 |
| 놓을 자리 | 작은 파란 고리 | **칸 전체가 눌린다** | 손이 이미 움직이는 중이라 작은 고리는 겨냥한 다음에야 보인다. 게다가 칸 전체가 곧 착지 판정 범위(`MonthGridGeometry`)라 **보이는 것과 되는 것이 같아진다** |
| 붐비는 날 | 캡슐 점 셋, 넷부터 막대 | **번진 잉크** | 아래 참조 |
| 달 이동 | `‹ ›` | **이웃 달의 이름** | 아래 참조 |
| 두 층의 경계 | 1px 실선 | **접힌 자리** | 실선은 위아래를 두 개의 판으로 가른다. 이 창의 요지는 두 층이 *한 장에* 있다는 것이다(§10.2). 접힌 자국은 가르면서도 한 장임을 말하고, 아래쪽 절반에 메모와 같은 도트 그리드를 깔아 **위는 보는 면, 아래는 적는 면**이라고 재질로 잇는다 |
| 다음 한 줄 | `＋ 이 날에 적기` | **비워 둔 줄** | ＋ 는 "채워라"라는 말이다(§14.1). 노트에서 한 줄 더 적을 자리는 그냥 비어 있다 |
| 지난 날 | 일괄 55% | **하루씩 마른다** | 어제와 3주 전이 같은 세기면 그것은 "물러남"이 아니라 그냥 회색이다 (`InkDrying`) |
| 이번 주 | 없었다 | **형광펜 자국** | 게으른 사람이 달력에서 보는 단위는 하루가 아니라 "이번 주에 뭐 있더라"인데, 주를 말하는 표시가 하나도 없어 오늘 칸을 찾은 다음 그 줄을 눈으로 다시 훑어야 했다. 자국이지 칸이 아니다 — 양 끝은 종이에 닿기 전에 흐려지고, 세기는 알아챌 수 있는 최소치다. 진해지면 그것은 자국이 아니라 *골라 놓은 줄*로 읽히고, 고르는 일은 밑줄이 이미 하고 있다. 얼룩과 **같은 `Canvas` 한 장**에 그린다 |

손으로 그린 것처럼 보이려면 흔들려야 하는데, **매 프레임 새로 흔들리면 그것은 손이 아니라 잡음이다.** 그래서 흔들림을 날짜에서 뽑은 씨앗으로 재현한다 (`PenHand` — SplitMix64). 오늘의 동그라미는 하루 종일 같은 모양이고, 내일은 새로 그은 것이 된다. 획은 `stroke` 로 그리지 않는다 — 굵기가 일정한 선은 손이 아니라 자로 읽히고, 그것이 아이콘에서 흘림선을 직접 만든 이유와 같다(§14.7). 중심선을 따라가며 법선 방향으로 폭을 보간해 가변 굵기 도형을 만든다.

**한 바퀴를 크게 넘겨 긋다가 줄였다.** 많이 넘기면 꼬리가 획을 가로질러 `e` 처럼 읽힌다 — 그건 동그라미가 아니라 낙서다. 한 번에 그은 것으로 보이되 닫히지만 않으면 충분하다.

### 10.4 밀도는 세는 대신 번진다

칸마다 "3" 이라고 적으면 날짜 숫자와 섞여 둘 다 안 읽힌다. 그래서 앞선 판은 색점을 최대 셋 찍고 넷을 넘으면 셋째를 막대로 늘였다. 읽히긴 했지만 그것은 **여전히 세는 표시**였고, 칸마다 뷰가 넷씩 생겼다.

지금은 뒷면에서 배어 나온 **잉크 얼룩**이다. 색은 그대로 따라오므로 "그 파란 거"를 자리로 기억하는 것은 그대로고, 달을 통째로 보면 이 달에 얼마나 바빴는지가 **얼룩의 지도**로 보인다. 건수는 곧 멎는 곡선으로 옮긴다 — 다섯과 여덟의 차이는 게으른 사람에게 아무 뜻도 없고, 선형으로 두면 붐비는 달에서 얼룩이 칸을 삼킨다.

두 번 고쳤고 둘 다 렌더를 보고서야 알았다.

- **처음엔 칸 한가운데에 두었다.** 그러면 숫자가 잿빛 원판 위에 올라앉아 "고른 칸"으로 읽힌다 — 여러 색이 섞이면 얼룩은 어차피 잿빛이 되므로 그것은 색이 아니라 부품으로 보인다. 숫자 **아래**로 내리니 숫자는 종이 위에 그대로 남았다.
- **처음엔 여러 색을 겹쳐 찍었다.** 섞여서 잿빛이 되어 색이 하는 일이 사라진다. 옆으로 늘어놓아야 색이 산다.

그리고 얼룩은 칸마다 그리지 않고 **격자 전체에 `Canvas` 한 장**으로 그린다 (`InkBleedLayer`). 격자가 균일하므로 얼룩의 자리도 산수로 나온다 — 앞선 판의 캡슐 점보다 오히려 레이어가 적다 (§14.8).

### 10.5 달 이동은 화살표가 아니라 이름이다

`‹ ›` 는 어느 앱에나 있는 부품이라 이 창이 무엇으로 만들어졌는지 말해 주지 않고, 무엇보다 **어디로 가는지 이름을 대지 않는다.** 이웃 달을 옅게 적어 두면(`7월  8월  9월`) 시간이 양옆으로 뻗어 있는 것이 그대로 보이고, 누르는 자리가 곧 도착지의 이름이 된다 — 철학 2(시간이 유일한 구조)가 머리에서 한 번 더 말해지는 셈이다. 평소엔 종이에 스민 정도로만 있다가 포인터가 오면 또렷해진다 (철학 4).

띠에 적히는 이름과 실제로 넘어가는 달이 어긋나면 누르는 자리가 도착지를 속이게 되므로, 열두 달 전부를 `MonthGrid.advanced(by:)` 와 대조해 테스트로 못 박았다 (`CalendarInkTests`).

### 10.6 좌표는 산수로 푼다

끌어다 놓기는 "포인터가 몇 일 칸 위에 있는가" 한 줄에 전부 걸려 있다. 칸마다 `GeometryReader` 를 심으면 화면에 뷰가 42개 더 생긴다 (§14.8 — 레이어 수가 곧 메모리 예산). 격자는 균일하므로 **격자 하나만 재고 나머지는 나눗셈으로 푼다** (`MonthGridGeometry`).

그리고 그 산수는 눈으로 확인할 수 없다 — 한 칸 밀린 것과 맞는 것이 화면에서 똑같아 보이고, 틀린 것은 다음 날에야 드러난다. §8.1 에서 세 번 틀린 것이 정확히 이런 종류였다. 그래서 뷰 밖의 순수 값으로 빼고 `MonthGridGeometryTests` 로 못 박았다.

### 10.7 나머지

- 쿼리는 SQLite 인덱스의 날짜 범위 조회로 처리. 격자가 덮는 범위(앞뒤 달 넘침 포함)를 그대로 넘긴다.
- EventKit 연동은 **읽기 전용으로만** 후순위 검토. 쓰기를 열면 LLM 이 사용자의 실제 캘린더를 수정·삭제할 수 있게 되어 위험이 급상승한다.
- **종이에서 건너와 놓을 날을 기다리는 모습은 `calendar-placing.png` 로 남긴다** (§7.3). 들고 있는 조각·놓을 자리·바닥의 「놓을 날을 고르세요」는 포인터가 달력 위에 있어야만 나타난다.
- **조작하는 중의 모습은 `calendar-in-use.png` 로 남긴다.** 집어 든 조각·놓을 자리·겹쳐 뜬 「미루기」·되돌리기 줄은 포인터가 있어야만 나타나므로, 연출하지 않으면 이 저장소에서 영영 확인되지 않는다. 그 렌더는 옮기기를 흉내 내지 않고 **실제로 시켜서** 그린다 — 그래야 그림이 곧 검증이다.

### 10.8 판형이 둘이다 — 세로로 선 창, 가로로 누운 창

배치가 하나뿐이면 **창 크기가 장식이 된다.** 이 창은 사용자가 마음대로 늘릴 수 있는데, 늘린 결과가 두 방향 모두에서 무너져 있었다.

- **세로로 늘리면** 격자는 그대로인 채 아래만 텅 빈다. 주 높이가 36pt 로 못 박혀 있어 창을 두 배로 키워도 달은 창 위쪽에 붙은 작은 표로 남았다.
- **가로로 넓히면** 칸만 옆으로 늘어난다. 날짜가 넓은 여백 가운데 떠 있고, 정작 조작하는 면(그 날의 일)은 여전히 창 아래 눌린 띠였다 — 폭은 남아도는데 목록의 폭은 그대로다.

그래서 판형을 둘로 나눴다 (`CalendarLayout`).

```
세로로 선 창                        가로로 누운 창
┌──────────────┐                  ┌────────────────────┬───────────────┐
│ 7월 8월 9월   │                  │ 7월 8월 9월                  2026 │
│ 일 월 화 …    │                  │ 일  월  화  수  목  금  토 ╷       │
│ …  …  …  …   │                  │  …   …   …   …   …   …   … │ 29    │
│ ─────╷────── │ ← 가로로 접힌다   │  …   …   …   …   …   …   ┤ 토요일  │  ← 세로로 접힌다
│ 오늘 · 8월 29일│                  │  …   …   …   …   …   …   … │ 09:30 │
│ ┃09:30 팀 회의│                  │  …   …   …   …   …   …   … │ 13:00 │
└──────────────┘                  └────────────────────┴───────────────┘
```

| | 세로로 선 창 | 가로로 누운 창 |
|---|---|---|
| 배치 | 위는 달, 아래는 그 날 | 왼쪽은 달, 오른쪽은 그 날 |
| 접힌 자리 | 가로로 눕고 고른 날의 **열**을 가리킨다 | 세로로 서고 고른 날의 **행**을 가리킨다 |
| 격자의 몫 | 남은 높이의 58% (아래도 조작하는 면이라 굶기지 않는다) | 남는 높이를 거의 다 쓴다 |
| 고른 날의 머리 | 목록 위의 한 줄 | 큰 날짜 + 요일 (건너온 눈이 처음 닿는 것이 "며칠"이어야 한다) |

문턱은 **비율과 폭 둘 다**로 잡는다. 가로가 세로의 1.15배를 넘고 폭이 430pt 이상일 때만 눕는다 — 정사각형에 가까운 창에서 두 면을 나란히 놓으면 격자는 칸이 좁아 겨냥이 어려워지고 목록은 제목이 잘려서 **둘 다 못 쓰게 된다.**

주 높이·펜 자국의 지름·숫자 크기는 두 판형 모두에서 창을 따라 자란다. 동그라미의 획 굵기까지 지름을 따라간다 — 굵기를 못 박아 두면 큰 칸에서 동그라미가 가는 철사처럼 보인다. 5주 달과 6주 달은 같은 창에서 **격자 높이가 같다** (주 수로 나눈다). 달을 넘길 때 아래 면의 높이가 출렁이면 목록이 매달 다른 자리에서 시작한다.

**창을 자기 자신으로 재면 안 된다.** 처음엔 `onGeometryChange` 로 뷰 스스로를 쟀는데, 그러면 돌아오는 것은 창이 아니라 **내용의 크기**다. 격자가 창보다 1pt 커지는 순간 그 큰 값이 다시 판형에 들어가 격자가 한 번 더 자랐고, 주 높이의 상한(64pt)에 닿아서야 멎었다 — 620×360 창에서 머리가 통째로 잘려 나갔다. `GeometryReader` 는 언제나 **제안된 크기**를 주므로 그 고리가 끊긴다. 그리고 자리를 먹는 것들(머리 36pt·요일 줄 15pt·접힌 자리 19pt)의 높이는 어림이 아니라 **약속**이다 — 셈이 실제보다 몇 pt라도 적게 잡으면 격자가 창을 넘고, 넘은 만큼은 잘려서 안 보인다.

산수를 뷰 밖(`CalendarLayout`)에 둔 이유는 §10.6 과 같다. 한 판형에서 맞고 다른 판형에서 어긋나는 것은 **그림 한 장으로는 확인되지 않는다** — 위의 잘림도 기본 창의 렌더는 멀쩡했다. 그래서 창 표본 여덟 개 × 주 수 셋을 훑어 "격자는 창을 넘지 않는다 · 펜 자국은 칸 안에 머문다 · 두 면이 폭을 나눠 갖는다"를 `CalendarLayoutTests` 로 못 박고, 넓은 창(`calendar-wide.png`)과 크게 늘린 세로 창(`calendar-large.png`)을 렌더로 남긴다.

## 12. 배포 (D7)

오픈소스. 길이 둘이고, **둘 다 1차다.**

### 12.1 소스 빌드 — 검역 딱지가 붙지 않는 유일한 길

```sh
git clone … && ./scripts/build-app.sh && open dist/LazyMemo.app
```

`swift build` 한 줄이고 Xcode 가 필요 없다. **직접 빌드한 앱에는 `com.apple.quarantine` 이 붙지 않아** Gatekeeper 가 애초에 관여하지 않는다. 이것이 처음부터 1차 경로였던 이유이고, 지금도 남는다 — 공증 없는 앱을 남에게서 받는 것이 꺼림칙한 사람에게 줄 답이 이것뿐이다.

### 12.2 Homebrew cask — `.app` 을 그대로 준다

```sh
brew tap bunhine0452/lazymemo
brew install --cask lazymemo
```

**앞선 판은 이 길을 권하지 않았다.** 근거는 이랬다 — "GitHub Releases 로 바이너리만 뿌리면 macOS 15 부터 우클릭-열기 우회가 사라져 사용자가 시스템 설정까지 들어가야 하므로 마찰이 크다." 그 관찰은 **지금도 사실이다.** 바뀐 것은 관찰이 아니라 **누가 그 마찰을 감당하는가**다.

- 검역 딱지를 붙이는 것은 **내려받는 쪽**이다. Homebrew 도 붙인다.
- 딱지가 붙은 미공증 앱은 macOS 15 부터 「손상되었습니다」로 끝난다.
- 그래서 cask 가 설치 직후 그 딱지를 뗀다 (`postflight` 의 `xattr -dr`).

**이것은 미봉책이고, 문서에 그렇게 적어 둔다.** cask 의 `caveats` 와 탭의 README 와 이 문단이 같은 말을 한다 — 떼어 냈다는 사실, 왜 뗐는지, 믿을 수 없으면 소스에서 빌드하라는 것. 조용히 떼는 것과 적어 두고 떼는 것은 다른 일이다.

떼는 것이 그나마 정당한 근거는 하나뿐이다: **그 zip 이 어디서 나왔는지 누구나 확인할 수 있다.** 같은 저장소의 태그에서 `scripts/package-release.sh` 하나로 만들어지고, 소스에서 빌드해 같은 것이 나오는지 대조할 수 있다.

옳은 답은 **Developer ID + 공증**이다. `notarytool` 은 CommandLineTools 에 이미 있으므로 인증서만 발급받으면 CI 에서 자동화된다. 받는 즉시 `postflight` 블록을 통째로 지우고 이 문단도 지운다.

### 12.3 태그를 밀면 그것이 곧 배포다

`.github/workflows/release.yml` — 태그 `v*` 가 올라오면 macOS 러너에서 시험을 돌리고, 번들을 조립하고, `ditto` 로 묶고, 릴리스를 만들고, 탭의 `sha256` 을 갱신한다.

손으로 하던 다섯 단계 중 **sha256 이 가장 위험했다.** 그 값이 틀려도 만든 사람 기계에서는 아무 일도 일어나지 않는다 — 오직 받는 사람에게만 「checksum mismatch」로 터진다. 만든 사람이 확인할 수 없는 값을 손으로 옮기고 있었다는 뜻이라, 그것 하나만으로도 자동화할 값이 있었다.

지키는 것 셋.

- **판이 어긋나면 시작도 안 한다.** 태그 · `Info.plist` · `Version.swift` 가 같은 판인지 먼저 본다. 어긋난 채 나가면 사용자가 받은 앱의 「정보」와 릴리스 이름이 서로 다른 말을 한다.
- **빨간 것은 내보내지 않는다.** 배포는 시험을 건너뛰기 가장 좋은 자리다.
- **묶은 것을 도로 풀어 서명을 다시 검사한다.** `zip` 은 확장 속성을 흘려 서명을 깬다 — 그러면 검역 딱지와 무관하게 안 열린다. 그래서 `ditto` 로 묶고, 풀어서 `codesign --verify` 를 한 번 더 한다.

탭은 다른 저장소라 기본 토큰으로 못 쓴다. `TAP_TOKEN` 시크릿이 없으면 **릴리스는 그대로 나가고** 탭 갱신만 건너뛰며, 무엇을 손으로 해야 하는지 실행 요약에 적는다.

### 12.4 소개 페이지

`site/` 를 GitHub Pages 로 낸다 (`.github/workflows/pages.yml`). 정적 파일 그대로이고 빌드 단계가 없다.

**바깥으로 나가는 요청이 하나도 없다** — 웹폰트도, 분석 스크립트도, 추적기도. 앱이 §9.3 에서 "기본 상태에서 네트워크를 쓰지 않는다" 고 약속했는데 그 앱을 소개하는 페이지가 추적기를 달고 있으면 그 약속은 거기서 깨진다. 워크플로가 배포 전에 그것을 실제로 검사한다.

- Developer ID 발급과 공증 — 받는 즉시 cask 의 검역 딱지 떼기를 지운다 (§12.2)
- homebrew-core 등록 — 지금은 개인 탭(`bunhine0452/homebrew-lazymemo`)이다. core 는 공증과 사용자 수를 본다
- 메모 수천 장 규모의 인덱스 갱신 전략 (현재 설계는 수백 장 기준)
- 창 24개 상한을 사용자가 조절할 수 있게 할 것인가

## 14. 디자인 철학 — 「흐릿하게 남는다」

이 앱은 사용자가 게으르다는 것을 결함이 아니라 **전제**로 삼는다 (§1). 그 전제를 끝까지 밀면 화면은 아래 네 문장으로 정해진다. `Sources/LazyMemoUI/Views/Theme.swift` 가 그 구현이다.

### 14.1 완성을 요구하지 않는다

쓰다 만 것, 제목 없는 것, 날짜 없는 것이 **정상 상태**다. 채우라는 표시도, 저장 버튼도 두지 않는다.

한때 이 문장을 "일정 없는 날은 아예 그리지 않는다"로 읽고 달력에서 빈 날을 지웠다가, 달 격자로 돌아오면서 되짚었다. **격자의 빈칸은 빈칸이 아니라 바탕이다** — 15일이 무슨 요일인지는 그 사이 아무것도 없는 칸들이 말해 준다. 채우라고 말하는 것은 빈 칸 자체가 아니라 "일정 없음" 같은 글자와 칸마다 붙은 ＋ 표시이고, 그런 것은 하나도 두지 않았다. 고른 날이 비어 있으면 그냥 아무것도 없다.

앱 아이콘의 흘러내리는 둘째 줄이 이 문장의 그림이다.

### 14.2 시간이 유일한 구조다

게으른 사람은 폴더도 태그도 유지하지 않는다. 유일하게 받아들이는 구조는 "언제"뿐이다. 두 가지가 여기서 나온다.

**달력은 보는 물건이 아니라 만지는 물건이다** (§10). 한 번은 반대로 갔었다 — 월 격자를 버리고 오늘부터 아래로 흐르는 목록(「흐름」)으로 바꿨다. "게으른 사람이 알고 싶은 것은 이번 달 지도가 아니라 다음에 뭐가 오나다" 라는 이유였고, **읽는 것에 대해서는 맞았다.**

틀린 것은 그 다음이었다. 게으른 사람이 달력에 가장 자주 하는 일은 보는 것이 아니라 **미루는 것**이고, 그 다음이 옮기는 것이다. 목록에는 날짜를 가리킬 자리가 없어서 두 동사가 통째로 화면 밖(메모 창·빠른 입력)에 남았다. 격자로 돌아온 것은 조망 때문이 아니라 **놓을 자리가 필요해서**다 — 날짜를 글자로 치지 않고 손으로 가리키려면 칸이 있어야 한다.

그래서 지금은 격자(조망·놓는 자리)와 고른 날의 목록(집는 자리)이 한 창에 위아래로 선다. 조망을 되찾으면서 조작을 얻었다.

**시간을 가리키는 말이면 무엇이든 앱이 스스로 읽는다** (`NaturalDateParser`). "내일 오후 3시 치과"라고 적으면 그것이 곧 일정이 된다. 사용자는 아무 형식도 배우지 않는다. LLM 없이, 네트워크 없이, 로컬에서. 이것이 §1 의 "정리를 대신 해준다"가 UI 에서 처음 실현되는 지점이다.

**네 나라 말을 함께 읽고, 언어를 고르게 하지 않는다.** 한국어·영어·일본어·중국어의 시간 낱말을 한 표(`TimeWords`)에 담았다. 설정에 "입력 언어" 항목이 생기는 순간 "아무것도 배우지 않는다"가 깨지므로, 표만 보고 섞어 적어도 그냥 읽는다. `내일 오후 3시` · `tomorrow at 3pm` · `明日の午後3時` · `明天下午3点` 이 모두 같은 곳에 닿는다.

**날짜뿐 아니라 하루 중 때도 읽는다.** `새벽`·`아침`·`점심`·`저녁`·`밤`·`자정`, 그리고 `morning`·`夕方`·`晚上`. 숫자가 붙어 있으면 그 숫자를 오전·오후로 갈라주고(`저녁 7시` → 19시, `밤 12시` → 0시), 숫자가 없으면 대표 시각으로 읽는다(`내일 저녁` → 19시). **여기가 앱이 짐작하는 유일한 자리다.** 그래도 짐작하는 쪽을 골랐다 — 시각을 적을 생각이 없던 사람에게 "몇 시?"를 되묻지 않기 위해서고, 해석 결과가 칩에 그대로 보이므로 어긋나면 바로 눈에 띈다.

칩에는 인식한 원문이 아니라 **해석한 결과**를 보인다 — "내일"이라고 되쓰면 제대로 읽었는지 확인할 수 없다. 그리고 인식한 조각은 본문에서 덜어낸다. "내일 오후 3시 치과"는 내일이 지나면 거짓말이 되기 때문이다.

**날짜 낱말이 없어도 때를 말로 밝힌 시각이면 읽는다.** `새벽 2시 기상` · `저녁 7시 약속` · `아침 회의` 를 그냥 넘기고 있었는데, 사람이 그렇게 적었다면 그건 명백히 일정이다. 못 읽으면 그 메모는 달력에도 없고 아무 때에도 떠오르지 않는다. 지난 시각이면 내일로 넘긴다 — 오후 3시에 "아침 회의" 라고 적었다면 그것은 내일 아침이다.

그러면서 맨 `3시에 전화` 는 **여전히 넘긴다.** 갈림길은 "어느 날인가" 가 아니라 **오전인가 오후인가** 다. `새벽`·`저녁`·`pm`·`15:` 는 글이 직접 말했고, 맨 `3시` 의 24시간제 값은 우리가 관행으로 고른 것이다(`byConvention`). 짐작 위에 또 짐작을 얹지 않는다.

한 가지 더 갈라 둔다 — 달력에서 날을 골라 놓고 `오후 3시 치과` 라고 적었다면 **고른 날이 이긴다.** 파서는 "다음에 오는 3시" 로 읽지만 그건 우리가 고른 날이지 사용자가 말한 날이 아니다. `Result.namesDay` 가 그 구분을 들고 다닌다.

욕심내지 않는다. 자주 쓰는 표현만 확실히 잡고 **애매하면 아무것도 하지 않는다** — 틀린 날짜를 자동으로 붙이는 것이 안 붙이는 것보다 나쁘다. `9/1` 같은 빗금 표기를 뺀 이유가 그것이다 ("3/4 컵"과 구별할 수 없다). 같은 이유로 영어는 낱말 경계를 지켜 읽고(`money` 에서 `mon`, `afternoon` 에서 `noon` 을 보지 않는다), `at` 없는 맨 숫자는 시각으로 보지 않는다 ("tomorrow 3 boxes" 는 세 시가 아니다).

### 14.3 오래된 것은 스스로 물러난다

정리하지 않는 사람의 바탕화면은 결국 낡은 종이로 덮인다. 그러니 시간이 지난 것이 조용히 **바래야** 한다 (`MemoAge`). 사용자가 아무것도 하지 않아도 화면이 정돈된다.

| 나이 | 기준 | 드러남 |
|---|---|---|
| `fresh` | 오늘 손댔거나, **아직 오지 않은 일정** | 100% |
| `recent` | 일주일 이내 | 88% |
| `settled` | 한 달 이내 | 72% |
| `faded` | 그보다 오래된 것 | 55% |

두 가지 예외가 규칙을 사람 편으로 만든다. **고정한 메모는 바래지 않는다** — 사용자가 직접 "이건 앞에 둬"라고 말한 것이라 시간이 그 뜻을 덮으면 안 된다. **다가오는 일정은 언제 적었든 또렷하다** — 앞으로 벌어질 일이기 때문이다.

포인터를 올리면 즉시 되살아난다. 읽으려는 뜻이 곧 되살리는 신호다.

규칙을 UI 밖(`LazyMemoCore`)에 둔 이유는 경계에서 틀리기 쉽고 눈으로 확인하기 어려워서다. 테스트로 못 박았다.

### 14.4 앱은 자기를 드러내지 않는다

**기본 상태의 메모는 글자와 종이뿐이다.** 머리글도, 아이콘 줄도, 색 점도 없다. 조작 버튼은 포인터가 올 때 내용 **위에 겹쳐** 뜨고 자리를 차지하지 않는다.

색은 **테두리와 왼쪽 위에서 번지는 잉크**로만 드러난다. 종이 전체를 물들이면 글이 읽히지 않고, 열 장이 겹치면 화면이 색종이가 된다. 창이 겹칠 때 실제로 보이는 것은 가장자리다.

**겹쳐 뜨는 조작은 첫 줄도 마지막 줄도 덮지 않는다.** 캡슐을 부르는 손짓(포인터 올리기)이 곧 **읽으려는** 손짓이므로, 읽으려고 다가가면 읽을 것이 가려지는 조작은 스스로를 문다. 다섯을 한 줄에 담았을 때 제목의 절반이 덮여서 ×만 위에 남기고 넷을 아래로 내렸는데, 그랬더니 이번에는 **꼬리(날짜·태그)가 덮였다** — 첫 줄 다음으로 비싼 줄이고, 날짜는 누르면 달력으로 가는 버튼이기도 하다.

두 줄을 다르게 푼다. 첫 줄은 **자리를 비우지 않는다** — 본문에 영구히 홈을 파면 적는 면이 좁아지고, 포인터가 올 때만 뜨는 조작이 늘 자리를 차지한다는 뜻이라 철학 4 를 어긴다. 대신 덮는 폭을 한 글자보다 좁게 유지한다. 꼬리는 반대로 **미리 비운다** — 그 오른쪽은 원래 거의 비어 있고, 비워 두면 태그가 길 때만 잘린다. **가려진 것은 가려진 줄도 모르고, 잘린 것은 잘린 줄 안다.** 두 숫자 모두 `NoteControlLayout` 한자리에 있고 시험이 지킨다 — 버튼 하나만 늘어도 캡슐이 조용히 되돌아오는데, 그 사실은 렌더를 눈으로 보기 전에는 드러나지 않는다.

### 14.5 재질은 하나 — 좋은 종이

`glassEffect` 를 쓰지 않는다. 메모에서, 달력에서, 빠른 입력에서 차례로 시도했다가 **모두 되돌렸다.** 반투명한 면 위의 글은 씻겨 나간다. 바탕화면 사진이 무엇이든 글은 읽혀야 하는데 유리는 그 통제권을 배경에 넘긴다.

그렇다고 **종이를 문자 그대로 흉내 내서도 안 된다.** 접착 메모지의 카나리아 노랑 바탕에 파란 가로 괘선을 그렸다가 되돌렸다 — 그건 현실의 종이가 아니라 2011년의 스큐어모피즘이고, 지금 보면 촌스럽다. 옛 메모 앱의 리갈패드가 그대로 떠오른다.

기준은 **좋은 노트**다 (무지·로이텀·필드노트).

| | 버린 것 | 지금 |
|---|---|---|
| 바탕 | 진한 카나리아 노랑 | 미색 오프화이트 (다크는 따뜻한 숯색) |
| 색 | 온 면을 물들임 | 종이에 7% 스밈 + 도트 그리드 색 |
| 결 | 가로 괘선 | **도트 그리드** — 지금 문구류의 언어이고 글을 줄에 맞출 의무가 없다 |
| 모서리 | 16pt (UI 카드) → 3pt (너무 날카로움) | 5pt |
| 여백 | 14pt | 20pt — 싸구려 메모지는 글이 가장자리에 붙어 있다 |

다크 모드에서는 밝은 종이를 그대로 두지 않는다. 어두운 화면에 흰 판이 박히면 눈이 아프다. 검은 문구류가 실제로 있고 그쪽이 훨씬 낫다 — 따뜻한 숯색 종이에 미색 잉크.

떠 있다는 느낌은 투명도가 아니라 **그림자와 크기와 자리**가 만든다.

**재질이 하나면 그 위에 놓는 표시도 하나여야 한다.** 이것을 늦게 알았다 — 달력은 종이 위에 서 있으면서 표시만 채운 원·테두리 원·캡슐 점·`‹ ›` 였고, 그래서 한 창만 남의 물건으로 읽혔다. 지금은 달력의 낱말이 전부 종이 위의 몸짓이다: 손으로 그린 동그라미, 밑줄, 번진 잉크, 접힌 자리, 비워 둔 줄 (§10.3). 재질을 정하는 것으로는 부족하고 **낱말까지 그 재질로 적어야** 화면 전체가 한 물건이 된다.

**예외를 하나 열었다 — 종이 투명도** (메뉴 → 설정). "반투명한 면 위의 글은 씻겨 나간다" 는 판단은 지금도 옳지만, **종이가 바탕화면을 덮는다**는 불편은 그것과 다른 종류의 불편이고 어느 쪽을 견딜지는 화면을 쓰는 사람이 정하는 편이 맞다. 대신 셋으로 조인다.

- 기본은 불투명한 종이 그대로다. 한 번도 손대지 않은 사람에게는 아무것도 달라지지 않는다.
- 네 단계로 끊고 바닥(0.35)을 둔다. 슬라이더는 조준해서 끌어야 하는 물건이고, 메뉴 안에서는 더 그렇다.
- **포인터가 오면 원래대로 진해진다.** 철학 3 의 "읽으려는 뜻이 곧 되살리는 신호" 를 그대로 쓴다 — 많이 비치게 두어도 읽을 수 없게 되는 순간이 없다.

### 14.6 빠른 입력은 화면이 정한 자리에 뜬다

`NSPopover` 를 메뉴바 아이콘에 매다는 방식을 버렸다. 아이콘이 어디 있느냐에 따라 위치가 흔들리고, 메뉴바가 붐벼 아이콘이 숨겨지면 엉뚱한 자리에 뜬다 (실제로 그렇게 나타났다). 게다가 주 경로는 단축키이고, 그때 사용자의 시선은 메뉴바가 아니라 화면 가운데 있다.

그래서 위치를 **우리가 정한다** — 마우스가 있는 화면의 위쪽 3분의 1. Spotlight 가 나타나는 자리이고, 사람들이 이미 훈련된 곳이다.

### 14.7 아이콘 — 쓰다 만 메모

종이 위에 첫 줄은 반듯하고, 둘째 줄은 끝으로 갈수록 가늘어지며 흘러내린다. 게으름을 **그릇의 모양이 아니라 글씨의 태도**로 말한다.

버린 안 셋과 이유를 남긴다.

| 안 | 기각 이유 |
|---|---|
| 굵은 `Z` 획 (잠·게으름) | 알파벳으로만 읽힌다. 폰트 회사 로고 같고 "메모"가 사라진다 |
| 아랫변이 처진 종이 | 둥근 사각형의 아래가 처지면 사람은 그것을 **말풍선**으로 읽는다 |
| 굵기가 일정한 흘림선 | 갈고리(✓)나 물결(~)로 읽힌다. 끝으로 갈수록 가늘어져야 "흐지부지"가 된다 |

그래서 흘림선은 stroke 가 아니라 **직접 만든 가변 굵기 도형**이다 (3차 베지에 중심선을 따라가며 법선 방향으로 폭을 보간). 판 모서리는 초타원(n=5) — `CGPath(roundedRect:)` 의 원형 모서리는 시스템 아이콘 옆에서 미묘하게 어색하다.

**디자인 파일이 아니라 코드가 원본이다** (`scripts/make-icon.swift`). 저장소에 출처를 알 수 없는 바이너리를 넣지 않고, 색·비례 변경이 diff 로 남으며, 누구나 재현할 수 있다.

### 14.8 레이어 수가 곧 메모리 예산이다

시각 결정은 곧 메모리 결정이다. 재디자인 도중 메모 10장 RSS 가 88.8MB → **99.9MB** 로 뛴 적이 있다. 원인은 창마다 늘어난 레이어였다 — 종이색과 세척색을 도형 두 개로 겹친 것, 그리고 색 띠를 모서리에 맞추려는 카드 전체 `clipShape`.

색을 미리 섞어 도형 하나로 칠하고 띠를 테두리로 옮겨 되돌렸다. 창 24개 상한(§7)도 같은 이야기다.

### 14.9 눈으로 확인하는 방법

화면 기록 권한이 없어도 UI 를 볼 수 있어야 한다. `./scripts/render-ui.sh` 가 **실제 뷰를** `ImageRenderer` 로 그려 라이트·다크를 나란히 낸다 (`build/ui/*.png`).

화면 밖 렌더의 한계 셋을 우회한다.

- `NSViewRepresentable`(편집기)은 그려지지 않는다 → `MemoTextArea` 가 같은 글꼴·여백의 `Text` 로 대체
- `ScrollView` 안의 내용이 그려지지 않는다 → 흐름은 스크롤 없이 편다
- `LazyVStack` 은 실체화되지 않는다 → 개수가 적으므로 `VStack` 을 쓴다

우회 여부는 환경값 `rendersStatically` 하나로 흐른다.

**렌더로 잡히지 않는 것은 눌러 본다.** 그림은 "무엇이 보이는가"까지만 말하고 "키가 어디로 갔는가"는 말하지 못한다. ⌘⌫ 가 고른 메모 대신 적던 글자를 지워도 그림은 똑같다 — 게다가 이 상자는 `.nonactivatingPanel` 이라 ⌘ 조합이 글 쓰는 곳까지 닿지 못한 전력이 있다(⌘V 가 죽었던 일). 그래서 앱 안에서 가짜 키·클릭을 만들어 흘려보내고 결과를 stderr 로 적는 통로를 둔다: `LAZYMEMO_DELETE=1`(`verify-capture-delete.sh`), `LAZYMEMO_DISMISS=1`(`verify-capture-dismiss.sh`), `LAZYMEMO_MENU=1`. 진단은 **끝나고 되돌려 놓는다.**

### 14.10 메뉴바 목록 — 줄을 직접 그린다

메뉴는 이 앱에서 유일하게 **시스템의 얼굴을 하고 있던 자리**였다. 종이와 잉크로 된 화면 옆에서 회색 시스템 목록만 남의 것처럼 보였고, 더 나쁜 것은 기능이었다 — 제목만 늘어서서 「빈 메모」가 세 줄 겹치면 어느 것이 어느 것인지 알 수 없었고, 체크 표시(✓)는 "바탕화면에 나와 있음"이라는 뜻인데 메모 앱에서 그것은 "다 한 일"로 읽혔다.

그래서 메모 줄만 `NSMenuItem.view` 로 직접 그린다 (`MemoRow`). 나머지 항목은 시스템 것을 그대로 쓴다 — 메뉴가 얻어 오는 것(키보드 이동, esc, 자리 잡기, 스크롤)을 포기할 이유가 없다.

한 줄에 넷이 있다.

| | 무엇 | 왜 |
|---|---|---|
| 왼쪽 | 종이 색 점. **찬 점 = 바탕화면에 있음, 빈 점 = 치워 둔 것** | 체크는 "다 한 일"로 읽힌다. 점은 이미 이 앱의 낱말이다 (철학 4) |
| 가운데 | 제목 한 줄 | |
| 오른쪽 | 시간 한 조각 (`MemoTimeLabel`) — `내일 15:00` · `3일 전` · `9/1` | 폴더도 태그도 유지하지 않는 사람이 받아들이는 단서는 "언제"뿐이다 (철학 2) |
| 오른쪽 끝 | 휴지통 | 목록에서 지울 길이 없던 것이 이 화면의 가장 큰 결함이었다 (§6) |

**휴지통은 평소에도 희미하게 보인다.** 포인터가 온 줄에서만 나타나게 하면 화면은 깨끗해지지만, 있는 줄을 모르는 조작은 없는 것과 같다. 그래서 24% 세기로 늘 켜 두고 포인터가 오면 또렷해지며, 그 위에 올라가면 붉은 원이 깔린다 — 누르기 **전에** 다른 종류의 버튼임을 말한다.

**골라진 줄은 그 메모의 종이색으로 깔린다.** 시스템 강조색(`selectedContentBackgroundColor`)을 쓰던 자리다. 그 파랑은 이 목록만 다른 앱에서 잘라 온 부품처럼 보이게 했고, 무엇보다 **같은 메모를 두 곳에서 다르게 그렸다** — 빠른 입력의 골라진 줄에는 그 메모의 종이색이 옅게 깔린다. 두 곳에서 같은 것을 다르게 그리면 사람은 그것을 두 개의 목록으로 배운다. 글자 색은 강조와 함께 뒤집지 않는다: 종이색 바탕은 옅어서 잉크가 그대로 읽히고, 뒤집으면 여덟 줄 중 한 줄만 다른 재질이 된다.

**나열하는 수를 12장에서 8장으로 줄였다.** 목록이 화면 높이를 채우면 그건 목록이 아니라 또 하나의 치울 거리다. 넘치는 것은 빠른 입력의 검색으로 간다.

곁들여 걷어낸 것: 「바탕화면 창 스파이크」는 개발용 통로라 ⌥ 를 눌러야 나오는 대체 항목으로 접었고, 「빠른 입력」에는 지금 걸린 단축키를 오른쪽에 적었다 — 메뉴를 여는 사람은 대개 단축키를 모르는 사람이고, 알고 나면 다시는 메뉴를 열지 않는다.

**확인하는 방법.** `NSMenu` 는 시스템이 띄우는 창이라 `ImageRenderer` 로도 화면 캡처로도 잡히지 않는다. 두 갈래로 나눠 본다 — 줄의 생김새는 `MemoRow` 를 그대로 떠내 메뉴처럼 생긴 판에 얹어 `menu.png` 로 내고(포인터가 없으므로 강조와 휴지통 위 상태를 연출해 넣는다), 메뉴가 실제로 지어지는지는 `LAZYMEMO_MENU=1` 로 항목을 적어 본다. 휴지통의 좌표는 `MemoRowGeometry` 로 떼어내 테스트로 못 박았다 — 몇 픽셀 어긋난 "눌렀는데 안 지워진다"는 화면을 봐서는 알 수 없다.

### 14.11 조용한 화면에도 이름은 있어야 한다

철학 4 를 끝까지 밀면 조작은 **그림 한 개**가 된다 — 종이 위의 다섯 버튼도, 목록 줄의 휴지통도, 달 이동도 글자가 없다. 눈으로 보는 사람에게 그것은 조용함이지만, VoiceOver 를 쓰는 사람에게는 「trash」·「xmark」·「pin」이라는 **영어 기호 이름**이 읽힌다. 조용한 화면이 거기서는 알아들을 수 없는 화면이 된다.

**새 낱말을 만들지 않는다.** 이미 붙여 둔 도움말이 곧 이름이다 (`SpokenHelp`) — 「지우기 — 메뉴의 되돌리기로 살릴 수 있습니다」에서 「—」 앞이 이름, 뒤가 힌트다. 눈으로 읽는 말과 귀로 듣는 말이 어긋나지 않고, 도움말을 고치면 소리도 함께 고쳐진다. 여러 조각으로 된 줄(목록의 한 줄, 달력의 칸)은 하나로 묶어 「제목, 시간」·「8월 31일 — 4개」처럼 한 번에 읽힌다.

## 15. 편집기 — 마크다운, 사진, 링크

### 15.1 글자를 바꾸지 않고 꾸민다

`**굵게**` 를 치면 그 자리에서 굵어진다. 하지만 **파일에는 여전히 `**굵게**` 가 저장된다.** 편집기가 들고 있는 문자열은 사용자가 친 마크다운 그대로이고, 우리는 그 위에 입힐 속성의 **구간만** 계산한다 (`MarkdownScanner` → `MarkdownStyler`).

원문을 건드리는 순간 셋이 한꺼번에 무너진다 — 정본이 마크다운이라는 D4, 한글 조합(§8), 그리고 되돌리기.

**마커는 커서가 놓인 줄에서만 보인다.** 이것이 "치는 대로 꾸며진다"를 완성한다 — `## 제목` 이 그냥 큰 글씨로 보이고, `[이름](주소)` 는 이름만, `![](attachments/…)` 는 아무것도 남기지 않는다(그림은 아래에 붙으므로). 체크박스는 `- ` 를 감춰 `[ ]` `[x]` 만 남기면 고정폭 글꼴에서 그 자체가 체크상자로 읽힌다.

감추는 방법은 **글자를 지우는 것이 아니라 보이지 않을 만큼 작게 만드는 것**이다. 파일은 그대로고, 그 줄로 커서를 옮기면 마커가 되돌아와 고칠 수 있다. 흐리게만 눌러 두던 앞선 판은 화면이 코드 편집기처럼 보여 촌스러웠다.

지원하는 것: 제목(`#`~`######`) · 굵게 · 기울임 · 코드 · 취소선 · 목록 · 인용 · 체크박스 · 링크 · 이미지.

**끝낸 체크박스는 줄을 긋고 물러난다.** 지우라고 하지 않는다 (철학 1).

조합 중에는 다시 꾸미지 않는다. 속성을 통째로 다시 까는 동안 조합 밑줄이 지워져 한글 입력이 어디까지 됐는지 알 수 없게 되기 때문이다.

### 15.2 사진은 Vault 안의 진짜 파일이다

붙여넣은 사진은 `<Vault>/attachments/<ulid>.<ext>` 로 저장되고 본문에는 `![](attachments/…)` 참조만 남는다 (`AttachmentStore`). 데이터베이스나 앱 전용 저장소에 넣으면 사용자가 Finder 로 열어볼 수 없고, 폴더를 통째로 옮기는 것만으로 동기화된다는 §5.1 의 약속도 깨진다.

**절대 경로를 쓰지 않는다.** 사용자가 Vault 를 iCloud 로 옮기거나 다른 기계에서 열면 절대 경로는 전부 끊어진다. 그리고 본문은 사용자와 LLM 이 쓰는 값이므로, `..` 나 `/` 로 시작하는 경로는 열어 주지 않는다.

원본 데이터를 그대로 옮긴다. 붙여넣기 판에 png·jpeg·heic·tiff 중 무엇이 들어 있는지 보고 그 형식으로 저장한다 — 다시 인코딩하면 화질과 용량을 괜히 잃는다.

**그림은 글 아래에 붙는다.** 글줄 사이에 끼워 넣으려면 §15.1 의 "글자를 바꾸지 않는다"를 어기고 원문을 숨기는 편법이 필요하고, 그러면 커서와 되돌리기가 어긋난다. 종이에 사진을 붙이는 것도 대개 글 아래다.


**높이에 뚜껑이 있고, 포인터를 올리면 원본 크기로 펼친다.** 처음에는 전폭으로 펼쳐 놓았는데 기본 창 크기(260×200)에서 그것이 메모를 통째로 잡아먹었다 — 글은 두 줄만 남고 사진은 종이 밖으로 삐져 나갔다. **붙여넣기는 되고 있었는데 화면에서는 "안 되는" 것으로 보였다.** 본문의 `![](…)` 는 꾸밈이 감추므로 정말로 아무 일도 일어나지 않은 것처럼 보인다.

그래서 사진 몫을 종이 높이에 비례해 나누고(40%, 여러 장이면 다시 나눔) 넘치는 것은 잘라 보인다. 종이는 글을 적는 곳이지 앨범이 아니다. 제대로 보는 것은 포인터를 올렸을 때이고, 그때 원본 파일을 다시 읽는다 — 화면에 들고 있는 것은 480px 로 줄인 그림이라(§11) 원본은 **보겠다는 뜻을 밝힌 그 순간에만** 읽는다.

**빠른 입력에도 붙은 사진이 보인다.** 말풍선에는 펼칠 자리가 없으므로 작은 조각으로 "붙었다" 만 말하고, 역시 포인터를 올리면 펼친다. 여기에 아무 표시가 없던 것이 "빠른 입력에 사진 붙여넣기가 안 된다" 의 정체였다.

**⌘V 는 메인 메뉴에 기대지 않는다.** macOS 는 표준 편집 단축키를 메인 메뉴를 통해서만 응답 체인에 흘려보내고(`StandardMenu`), 그 단축키는 앱이 활성일 때만 산다. 그런데 빠른 입력 상자는 `.nonactivatingPanel` 이다 — 활성화가 늦거나 거절되면 **글자는 쳐지는데 ⌘V 만 죽는다.** 창의 `performKeyEquivalent` 는 메인 메뉴보다 먼저 불리므로 `MemoNSTextView` 가 거기서 직접 집는다. 메모 창도 같은 길을 타므로 두 곳의 동작이 갈리지 않는다.
### 15.3 링크는 네트워크 없이 임베딩한다

붙여넣은 URL 은 `[example.com/recipes](https://example.com/recipes)` 형태의 마크다운 링크가 되고, 편집기에서 파랗게 밑줄 쳐져 **한 번 눌러 열린다.**

이름은 **주소 자체에서만** 만든다 (`LinkLabel`). 페이지를 열어 제목을 가져오면 보기에는 좋지만, "기본 상태에서 lazymemo 는 네트워크를 쓰지 않는다"(§9.3)는 약속이 그 순간 깨진다. 메모를 적는 것만으로 바깥에 요청이 나가서는 안 된다. 대개 그것으로 충분하다 — 사람은 `github.com/lazymemo` 만 봐도 무엇인지 안다.

**클릭 규칙:** 편집 중이 아니면 링크가 열리고, 쓰고 있는 중이면 커서가 놓인다. ⌘클릭은 언제나 연다. 언제나 열면 링크 글자를 고칠 수 없고, 언제나 커서만 놓으면 붙여넣은 링크가 장식이 된다.
